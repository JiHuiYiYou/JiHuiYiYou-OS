## § 1 锁 6 件事

### 1.1 消息格式:Type-driven IPC(2026-08-04 锁)

**决策**: IPC 消息 = jhyy 类型,编译器验证 handler 签名。

#### 1.1.1 设计

```jhyy
// 消息类型(用户定义)
type PageFaultMsg = struct {
    addr: u64,
    access_type: AccessType,   // Read / Write / Exec
    cap: Cap<Page>,            // 关联 cap
};

// handler 签名(编译器验证)
fn handle_page_fault(msg: PageFaultMsg, env: *Env) -> Reply {
    // ...
}

// IPC 调用(语言级)
let reply = ipc_call(endpoint_cap, PageFaultMsg { addr, access_type, cap });
```

#### 1.1.2 编译期检查

| 检查项 | 实现位置 | 拒绝什么 |
|--------|---------|---------|
| handler 签名匹配消息类型 | sema | handler 拿错字段 / 多余字段 |
| handler 返回类型 = Reply | sema | 漏返回值 |
| endpoint cap 类型 = `Cap<Endpoint>` | sema | 用 `Cap<File>` 当 endpoint |
| payload 大小 ≤ syscall ABI 上限 | sema | payload > 4KB(避免 1 syscall 太大) |

#### 1.1.3 wire format

- **消息体**:struct pass-by-value ABI(jhyy ABI v1.0.0 § 3.2)— 调用方栈副本 + sret
- **header**:定长 16 字节 = `{ endpoint_idx: u32, msg_size: u32, msg_tag: u32, reserved: u32 }`
- **payload**:`header + msg` 一起通过寄存器 + 栈传递(跟 Windows x64 一致)
- **大于 4KB**:走共享内存 + Cap<Shm> 引用,不走 syscall payload

⚠️ **P0-3 syscall 寄存器约定需独立定义**:`syscall` 指令硬件行为会**毁掉 RCX(return RIP)+ R11(RFLAGS)**;jhyy 继承 MS x64 把第一个整型参数放 RCX → 冲突。Linux 的解法是把 syscall arg1 从 RCX 挪到 R10。当前文档"payload 通过寄存器 + 栈传递(跟 Windows x64 一致)"对**用户态函数调用**成立,但**对 syscall 边界**不成立:需要独立的 syscall ABI 寄存器表(R10 顶替 RCX,header/mmsg 各放哪几个,待 OS 团队拍)。另外 struct return 走 sret 意味着内核要往用户给的指针写,指针要做完整地址空间校验(copy-in/copy-out 语义);该校验路径当前未写。

#### 1.1.4 优势

- 编译器验证 handler 不漏字段 / 不拿错字段 → 编译期消除一整类 IPC bug
- 消息类型 = jhyy struct → ABI 已有(sret),无新协议设计
- Cap\<T\> 跨 IPC 走 phantom type 序列化(8 字节 cnode 引用,接收端重建 Cap\<T\>)

✅ **2026-08-05 闭环**(per coordination.md § 3 D16 / Q-OS-007):Cap 跨 IPC 时 `cnode_idx` 是发送方 namespace 相对,接收方需不同的 `cnode_idx` → 内核必须**在消息 payload 内部原地改写** Cap 字段。要原地改写,内核就得知道"用户自定义 struct 里 Cap 在哪个 offset" → **编译器为每个含 Cap 的消息类型生成 cap-offset 表**(由 16 字节 header 里的 `msg_tag` 索引)。**实现路径**(D16):主路径 codegen 内联到 syscall wrapper;次路径 metadata 段 emit;复用 struct field offset 表;ABI § 12 wire 形式 `{msg_tag: u32, n_caps: u16, cap_offsets: [u16; n]}`。这条正中原则 #5("kernel 绝不解决语言问题")。

#### 1.1.5 备选(锁前讨论)

- ❌ **定长 header + 变长 payload(传统 microkernel)** — 编译器无法验证 payload 合法性,失去 type-driven 优势
- ❌ **全 inline 寄存器(zero-copy)** — Cap 跨 IPC 还得序列化,得不偿失
- ✅ **Type-driven IPC** — 编译器验证 + ABI 复用 + 优雅

### 1.2 capability 传递 / 派生 / 复制

- **传递**:消息里包含 `Cap<T>`,通过 IPC 跨进程
- **派生**:`derive(parent: Cap<T>, restrictions: Caps) -> Cap<T>`(限制子集)
- **复制**: ❌ `Cap<T>` 不能跨进程复制,只能 grant

详见 [v0.0.1-capability.md § 1](v0.0.1-capability.md)。

### 1.3 同步 RPC + 超时协议

- **同步 RPC**:`ipc_call(endpoint_cap, msg) -> Reply`,阻塞直到 reply 或 timeout
- **超时**:`ipc_call_with_timeout(endpoint_cap, msg, timeout_ns) -> IoResult<Reply>`,timeout = 错误码 `ErrTimeout`
- **时间类型**:`u64` 纳秒数(相对时间,从 IPC 调用开始算)
- **错误码**:timeout 是普通错误码,不单独走事件流(简化)

### 1.4 错误码体系:类型化 enum(2026-08-04 锁)

**决策**: 错误码 = jhyy enum + payload,编译器验证处理逻辑。

#### 1.4.1 设计

```jhyy
// OS 错误码(jhyy std/os/error.jhyy)
type SysError = enum {
    Ok,
    ErrNoEnt,                  // 文件/对象不存在
    ErrPerm,                   // 权限不足(由 cap rights 决定)
    ErrInvArg,                 // 参数非法
    ErrNoMem,                  // 内存不足
    ErrIo,                     // 底层 I/O 错误
    ErrTimeout,                // 超时
    ErrBusy,                   // 资源忙
    ErrExists,                 // 已存在
    ErrCapRevoked,             // cap 已被撤销(运行期)
    ErrNotCap,                 // 不是合法 cap(运行期兜底)
    ErrOther(i32),             // 其他(带 i32 子码)
};

type IoResult<T> = enum {
    Ok(T),
    Err(SysError),
};

// 用法(类型化)
match ipc_call(ep, msg) {
    IoResult::Ok(reply) => handle_reply(reply),
    IoResult::Err(SysError::ErrNoEnt) => handle_not_found(),
    IoResult::Err(SysError::ErrTimeout) => retry_with_backoff(),
    IoResult::Err(other) => panic_unexpected(other),  // 兜底
}
```

✅ **2026-08-05 闭环**(per coordination.md § 3 D17 / Q-OS-009):`Cap<T>` 不需要泛型(编译器当内建类型在 sema 硬编码,见 v3.x-capability-spec § 8);但 `IoResult<T>` 是**用户定义泛型**;lang-spec v1.1.0 enum 是单态的(无类型参数,见 spec 行 1196 "泛型:否")。**采用路径 A**(D17):MVP M1-M10 把 `IoResult` 单态化成 `IoResultUsize` / `IoResultReply` / `IoResultUnit` 三个具体 enum 手工展开。M11 升级路径:等 sprint 3i 加 generics 后,`IoResultXxx` 可手动合并回 `IoResult<T>`(`type alias` + 单态化 codegen 自动化),**非必须**。受影响代码:
- syscall-abi § 1.4.1: `IoResult<T>` → `IoResultUsize` / `IoResultReply` / `IoResultUnit` 三个具体 enum
- syscall-abi § 1.1.1: `type PageFaultMsg` 用 `[*]u8` 切片,本身不受影响
- process-model § 5.1: `fn use_cap_responsibly` 返回 `IoResult<()>` → `IoResultUnit`

#### 1.4.2 编译期检查

- `match SysError` 必须穷尽(lang-spec § 11.3 已有)— 漏 `ErrCapRevoked` 编译错误
- 不需要 switch-case fallback 写法,enum 强制覆盖
- `Err(i32)` 子码用于 OS 内部 debug,默认 panic

#### 1.4.3 优势

- 编译器强制错误处理(Rust 风格,但 jhyy 已有)
- 错误码新增 = 加 enum variant → 编译器强制所有 match 更新
- 类型化错误链(§ 5 walkable error chain)→ agent-friendly debug

#### 1.4.4 不仿 POSIX

- POSIX errno = 全局可变 int,丢失所有类型信息
- 进程 A 的 errno = 5,进程 B 可能重置过,无 provenance
- jhyy 方案 = enum 强类型 + payload 携带子信息

### 1.5 endpoint 命名空间(2026-08-04 锁)

**决策**: per-process capability namespace(走 Cap<Endpoint>,不靠全局名)。

#### 1.5.1 设计

- 全局 endpoint 表 = kernel-only,user 看不见
- user 持有 `Cap<Endpoint>`,Cap 引用 = 命名 + 权限
- 跨进程 endpoint transfer 走 grant()(跟其他 Cap 一致)

#### 1.5.2 为什么不是全局名

- 全局 endpoint 名 → 跟 fd 一样可伪造
- Cap<Endpoint> → 编译期类型 + phantom 保证安全
- namespace 隔离 → process A 的 endpoint 不影响 process B

#### 1.5.3 进程如何获得初始 endpoint

- init 进程由 kernel 创建,持有 root endpoint
- 通过 grant() 链式分发给子进程
- 类 Unix `init` → service → user 进程的链

## § 2 Boot 路径(2026-08-04 修订)

### 2.1 锁定的引导路径:UEFI + PE/COFF

```
jhyy 编 kernel.efi (PE/COFF) → QEMU -bios OVMF -kernel kernel.efi
```

- **不需要** QBE ELF 后端(v2.x 工作可推迟)
- OVMF(QEMU UEFI firmware)原生支持 PE/COFF
- 实机 boot 同路径(USB EFI 应用)

### 2.2 boot stub 需求(2026-08-04 spike 验后)

- ~~real mode → protected mode → long mode 切换~~ ❌ — UEFI x64 固件交接时已在 long mode + 分页启用 + identity-map,**无模式切换**。spike 验证:`EFIAPI efi_main(ImageHandle: EFI_HANDLE, ST: *SystemTable)` 用 MS x64 调用约定,无需任何 inline asm。这一段从 legacy BIOS 心智模型抄的,已删除。
- 页表建立(asm + volatile,sprint 3a-3f 需要 —— **kernel 自己**的页表,不是 EFI 的)
- framebuffer 获取:**UEFI GOP 走 EFI 函数指针**(`BootServices->LocateProtocol` + `GOP->Mode->FrameBufferBase`),`extern fn` 原生支持,**不需要 asm syscall-like**。spike 验过 ConOut 走同样模式,BootServices 函数指针偏移待 v0.0.3 / v0.1+ 实施时核(可能因 OVMF 版本而异,详见 spike 教训)
- 跳入 kernel entry(asm + `#[link_section = ".text.boot"]` —— 保留:这是 kernel 边界,不是 UEFI 边界)

**注意 UEFI 入口约定**(spike 实测踩坑,落到 memory `feedback_uefi_x64_conventions.md`):
- **RCX = ImageHandle,RDX = SystemTable**(不是 RCX=ST)
- EFIAPI = MS x64,protocol 函数第一参数是 `*This`(走 RCX),不是自动塞

### 2.3 备选(推迟)

- **Multiboot2 + ELF** — 需 v2.x QBE ELF 后端重写
- 当前不实现,v3.x+ 视情况启用(legacy BIOS / 自定义 bootloader 场景)

### 2.4 双引导路径总览

| 路径 | 何时用 | 何时解锁 |
|------|--------|---------|
| **UEFI + PE/COFF**(锁) | MVP / 主流 | M1 时已可用 |
| Multiboot2 + ELF | legacy BIOS | v2.x QBE ELF 后端后 |
