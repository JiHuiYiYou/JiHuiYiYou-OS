## § 2 M5b 触发顺序

```
v1.0 closure
  ├── v2.0 amd64_win_freestanding target + hello.efi demo  (∥ v3.0,两层独立)
  └── v3.0 3a → 3b → 3c → 3d → 3e → 3f
                │
                ▼
               M1 (kernel 启动)
                │
                ▼
               M2 (cooperative scheduler)
                │
                ▼
               M3 (syscall ABI)
                │
                ├── v3.1 3g → 3g.5 → 3g.7  (∥ M2-M3 OS 实施)
                │
                ▼
               M4 (capability 落地)
                │
                ▼
               M5b (IPC 实现)
```

**细节**(2026-08-05 校准):
- v2.0 跟 v3.0 **并行**(target 层 vs 语言层)— 两层独立,但都要 M1 启动前完成
- M1 = kernel 启动(printk),依赖 v2.0 freestanding target + 3a+3b+3c+3d+3e+3f(v3.0 P0 全套)
- M2 = cooperative scheduler(单核),依赖 M1
- M3 = syscall ABI(消息类型 + ipc_call 内核函数),依赖 M2
- M4 = capability 落地(Cap<T> 在 sema + phantom layout + cap table 联调),依赖 M3 + v3.1 3g+3g.5+3g.7(在 M3-M4 之间完成;v3.0 末启动 v3.1 后即可)
- **M5b = IPC 实现(syscalls + capability 转移)**,依赖 M4

## § 3 M5b 实现要点

### 3.1 userland 侧

- `ipc_call(endpoint_cap, msg) -> IoResult<Reply>` 函数
- Type-driven IPC 编译器验证(sema 检查 handler 签名)
- Cap grant 走 syscall(用户代码不直接调用 grant fn,只调 ipc_call)

### 3.2 kernel 侧

- syscall handler 解析 message header(endpoint_idx + msg_size + msg_tag)
- cnode 实际检查(运行期兜底,L3 TCB)
- endpoint 找到目标进程 + 投递 message
- reply 路径:阻塞直到目标 reply 或 timeout
- timeout 用相对时间(u64 纳秒)

### 3.3 Type-driven IPC 落地

- sema 检查 handler 签名:`fn handler(msg: M, env: *E) -> Reply` 严格匹配
- sema 检查消息字段访问:handler 不能越界访问未声明字段
- sema 检查 endpoint cap 类型:`Cap<Endpoint>` 才能 ipc_call

### 3.4 Capability 跨 IPC

- 消息里包含 `Cap<T>` → 8 字节 cnode 引用
- 接收端:内核解析 cnode 引用,验证 rights,授予接收进程对应 cap
- 失败(已 revoke / 无权限)→ syscall 返回 `ErrCapRevoked`

## § 4 M5b 不需要的特性

为了避免过早扩张范围:

| 不需要 | 理由 |
|--------|------|
| generics(v3.x sprint 3i)| M5b 用具体类型,不需要 `Vec<T>` 等泛型 |
| closures(v3.x sprint 3j)| handler 显式 `fn + struct env`,无闭包需求 |
| async(v3.x+)| M5b 是同步 RPC,async 推迟到 v3.x+ |
| RAII / 自动析构 | jhyy spec 不支持,显式 revoke 模式 |
| nested fns | jhyy spec 不支持,顶层 fn only |

详见 [v0.0.2-foundation-revision.md § 6](v0.0.2-foundation-revision.md) MVP coding style。
