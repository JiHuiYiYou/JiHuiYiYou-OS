# v0.0.0 — jhyy_OS 设计骨架

**状态**: 讨论稿 → 已锁(2026-08-03)
**后续**: v0.0.1 三章联动 design doc 在此骨架上落地

## § 0 文档定位

本文档 = jhyy_OS 第一份正式设计稿。0 行代码,纯设计讨论。后续 v0.0.1 三章联动 design doc 锁 syscall-abi / capability / process-model 三块,本文档作为其锚点。

## § 1 使命

做一个**真自举完整闭环**的 OS + 语言样本:
- 单一语言栈(jhyy)覆盖 kernel / driver / shell / app / build tool
- 自举完整 = `jhyy 编 jhyy 编 jhyy 编 OS`(Oberon 级别 + capability 语言级)
- 学术价值 = 100%, 商业价值 ≈ 0, 过程价值 = 高

## § 2 核心约束(五原则)

锁,作为 § 4 所有开放维度选项的过滤器:

1. **可行且简单** ——任何决策先用"两个人能在 v0.x 阶段 hold 住"的尺子量
2. **双线作战是核心优势** ——jhyy 和 jhyy_OS 互相喂养, 反馈循环 = 周级
3. **项目初期寄生 Windows** ——开发 / 构建 / 调试在 Windows 上;OS 运行时脱离 Windows
4. **Debug 在语言里,不靠 gdb** ——编译期消除 bug 类 + 类型化错误链 + capability provenance + 类型化内核状态,让 solo developer 能独立 debug kernel,不依赖 gdb / kdb / printk
5. **Kernel 绝不解决语言应该解决的问题** ——任何 kernel 设计难,先问"是语言该加 feature 还是 kernel 该 hack"。过程级约束,贯穿整个 OS 设计生命周期

## § 3 非目标(故意不做清单)

- ❌ 抢 Linux 市场
- ❌ POSIX 兼容
- ❌ formal verification (seL4 风格)
- ❌ aarch64 v0.x(留 v0.5+ 视情况)
- ❌ GPU driver
- ❌ SMP v0.x(M1-M9 单核足够)

## § 5 决策顺序

按"先决条件 → 后决条件"递进:
1. ISA + 引导链(物理前提)
2. 内存模型(虚拟化前提)
3. 进程模型(地址空间 + 线程)
4. capability 安全模型(进程模型之上)
5. syscall ABI(capability 之上)
6. driver 模型(IPC 之上)
7. 文件系统 / VFS(IPC 之上)
8. UI / shell(syscalls + FS)

### C 端冻结时机(2026-08-04 修订)

- v1.0 closure = C 端冻结 = `jhyy_v_1 编 jhyy_v_0 出 jhyy_v_1` byte-equal
- v1.0 closure ≠ OS 可编(缺 6 P0)
- **v2.x N 代 = C 端冻结 + jhyy 端成熟**,这期间 OS 团队**只能**推 v0.0.x 设计 doc,**不能**用 C 端临时编 OS 原型(C 版 jhyy.exe 缺全部 6 P0 特性,编不出 OS — 见 `memory/project_jhyy_os_kickoff.md` "纯 jhyy from day 1 精确语义")
- **v3.x P0 完成 = OS 真启动硬前置**(M1 = v0.1.0)

## § 7 跨项目约束

- **OS 启动硬前置** = `jhyy_v_N 编 jhyy_OS` = v1.0 closure + v3.x P0 + 实战反馈
- **OS 反向影响编译器** = v3.x P0 必须含 capability 编译期检查
- **不要同时激进** = jhyy 编译器 v0.8 wip ↔ jhyy_OS v0.0.x 设计
