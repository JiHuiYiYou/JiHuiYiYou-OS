## § 1 Cap 类型设计

```jhyy
type Cap<T> = struct {
    cnode_idx: u32,    // cnode 表里的索引
    depth: u8,         // capability 在 cnode 树里的深度
    rights: u16,       // 权限位（读 / 写 / 授予 等）
    _phantom: *T,      // phantom type 字段（编译期存在，运行时 0 字节）
}
// 总运行时大小: 8 字节（cnode_idx 4 + depth 1 + rights 2 + 1 padding）

type File = struct { _priv: () }    // phantom, zero-sized
type Socket = struct { _priv: () }
type Process = struct { _priv: () }
type Endpoint = struct { _priv: () }
```

- `Cap<File>` 和 `Cap<Socket>` 编译器层不可互换(phantom type 强制)
- wire format = 8 字节 = `{ cnode_idx: u32, depth: u8, rights: u16 }`(seL4 风格 cnode 引用布局)
- phantom type 用现有 v1.0 类型系统即可,**不需 v3.x P0**
- ABI 锁定位置: `jhyy-abi-v1.0.0.md § 12`(待增,跟 compiler v3.x-capability-spec.md § 内存布局对齐)
- 跟 jhyy v3.x-capability-spec.md 8 条规则对齐:不可伪造 / 类型参数化 / 不可复制 / 不可降级 / 可撤销 / 空 capability / 传参 = move / `&mut` 借用一致

✅ **2026-08-05 锁(per coordination.md § 3 D6 + Q-OS-007/Q-OS-008 闭环)**:字段布局 = `cnode_idx(u32) + depth(u8) + rights(u16)` = 8 字节(中间 padding 在 offset 5,1 字节),seL4 风格。wire format 跨 IPC 由 `D16 cap-offset 表` 兜底(编译器生成,内核按 offset 改写,中间 padding 字节语义由编译器显式管理,sprint 3g 实现)。**字段重排建议(cnode_idx+rights+depth)不再采纳** — 选原序是为 seL4 cnode reference 兼容性 + 代码可读性(depth 在 cnode_idx 之后是 cnode 树自然顺序)。

## § 2 操作

```jhyy
// 派生 / 转移 / 撤销
fn derive<T>(parent: Cap<T>, restrictions: Caps) -> Cap<T>   // 派生(限制子集)
fn grant<T>(src: Cap<T>, dst: Cap<Process>)                  // 转移(跨进程)
fn revoke<T>(c: Cap<T>)                                       // 销毁

// 编译期元数据
fn provenance<T>(c: Cap<T>) -> ProvenanceInfo                 // debug 才有意义
fn is_valid<T>(c: Cap<T>) -> bool                              // 检查非 null

// 降级(必须 unsafe block + WaiverCap privilege)
unsafe fn into_raw<T>(c: Cap<T>) -> *u8                        // 显示降级,编译器警告
```

- 只能通过 syscalls 调用,不能 user mode 伪造
- 编译器阻止 + kernel 检查 token

## § 3 语言级约束(锁 3 条)

### 3.1 约束 1: Cap = 不透明 token + phantom type
- 编译器层 `Cap<File>` ≠ `Cap<Socket>`
- 伪造 fd = 编译错误

### 3.2 约束 2: capability 操作 = 语言级 const fn, compile 到 syscall
- `derive / grant / revoke` 都是语言级 const fn
- 编译到 syscall,不能 user mode 伪造
- 编译器阻止 + kernel 检查 token

### 3.3 约束 3: syscall 签名只接 Cap<T>, 不接 u64
```jhyy
extern fn sys_read(f: Cap<File>, buf: *mut u8, len: usize) -> IoResult<usize>;
```
- 编译期阻止 `sys_read(0x1234 as u64 as Cap<File>, ...)`
- `u64` → `Cap<T>` 的 `as` 转换必须是 syscall 的结果

## § 4 Narrow Waivers 设计(2026-08-04 锁)

**问题**: 99% capability 安全保证由编译器层做,但总有些角落情况编译器无能为力(legacy 互操作 / 硬件直接访问 / kernel 模块加载 / 用户特殊需求)。

**设计**: 编译器做主,运行期做兜底,显式而非隐式。

### 4.1 三层检查

| 层 | 占比 | 触发条件 | 实现 |
|---|------|---------|------|
| **L1 编译期** | 99% | 普通 Cap 操作 | phantom type + 类型规则 + linter |
| **L2 Narrow Waiver** | < 1% | 显式 `unsafe_cap { ... }` block | 编译器警告 + 运行期单 bit 检查 |
| **L3 Kernel 强制** | 兜底 | syscall 实际执行 | cnode 检查 + rights bitmask |

### 4.2 `WaiverCap` privilege

进程 capability 表里加一个 single bit:

```
struct ProcessCaps {
    caps: [Cap<T>; N],      // 进程持有的 capabilities
    has_waiver: bool,       // WaiverCap — single bit
}
```

- 没 WaiverCap → `unsafe_cap` block 编译通过但运行期 abort
- 有 WaiverCap → `unsafe_cap` block 运行期放行(仍编译器警告)
- 默认 = false,只有 kernel 显式 grant 才 = true(类似 setuid)

### 4.3 `unsafe_cap` 语法(proposed)

```jhyy
// 普通代码:编译期就拒绝
fn dangerous_low_level(c: Cap<RawDevice>) -> i32 {
    c.into_raw();             // ❌ 编译错误:Cap<T> 不能隐式降级
}

// waiver 路径:显式 unsafe block + WaiverCap 检查
fn legacy_interop(c: Cap<File>) -> i32 {
    unsafe_cap {              // ⚠️ 编译器警告:unsafe_cap 块
        let raw = c.into_raw();   // 显式降级
        legacy_syscall(raw)
    }
}
```

### 4.4 Layered TCB

```
L1 编译器(主) → L2 Waiver(兜底) → L3 Kernel syscall(强制)
   99% checks         < 1%             100% ground truth
```

- L1 通过 + L2 通过 + L3 通过 = 执行
- L1 失败 → 编译错误(永不执行)
- L1 通过 + L2 失败 → 运行期 abort(优雅)
- L1 通过 + L2 通过 + L3 失败 → syscall 错误(降级)

**关键洞察**: L2 不是 L1 的替代,是 L1 的补丁。L1 fail-loud(编译错误)> L2 fail-fast(运行期 abort)> L3 fail-safe(降级)。

### 4.5 为什么不是 "全部 L3"(纯运行期方案)

- 运行期每次 syscall 都检查 cnode → 性能损耗
- 编译期能拒的(fake cap / wrong type)就不该到运行期
- Layered TCB = 编译期拒 99% + 运行期兜 1% = 性能 + 安全双赢

## § 5 Compile-time capability provenance(2026-08-04 锁)

**问题**: runtime debug 时,`Cap<T>` 只是个 8 字节值,丢了所有 provenance 上下文 —— 谁构造、什么时候、被谁 grant、经过几条链。

**设计**: debug build 时,每个 Cap 携带 provenance metadata,release build 可 strip。

### 5.1 ProvenanceInfo 结构

```jhyy
type ProvenanceInfo = struct {
    constructed_at: SourceLoc,          // 构造点(file + line + column)
    constructed_by: FnId,               // 构造时所在的 fn(`kernel_alloc_page` 等)
    grant_chain: *ProvenanceInfo,       // grant 历史(via grant());NULL 结尾单向链,NULL = root
    revoke_chain: *ProvenanceInfo,      // revoke 历史(via revoke());同上
    current_holder: ProcessId,          // 当前持有者
    rights: u16,                        // 当前 rights
    created_at_ns: u64,                 // 构造时间戳(ns,运行期基线)
}
```

> **D40 修订(2026-08-12)**:`grant_chain` / `revoke_chain` 原为 `[*]ProvenanceInfo`(jhyy slice,16B = ptr+len),与 wire-format 的单 ptr(8B)构成两种视图,且 `len` 语义从未定义。现按 D40 规则(**wire-format 有显式 `*_len` → slice;NULL 结尾链 → 裸指针**)统一为 `*ProvenanceInfo`。语义不变(本来就是单向链),两侧尺寸自此一致(均 136B,含 DAG 扩展)。详见 [`v0.0.4-debug-abi.md § 7.5`](v0.0.4-debug-abi.md)。
> D14 主体决策(provenance 是 OS 独有 debug / 不进 std / debug build side table / `Cap::provenance()` 接口)不变。

### 5.2 实现:side table

- debug build:每个 process 维护 `ProvenanceTable [CapId] -> ProvenanceInfo`
- 写时同步:每次 `derive / grant / revoke` 更新对应 entry
- release build:side table 可 strip(默认 strip)
- access:`Cap::provenance()` → 查询 table → 返回 `ProvenanceInfo`

### 5.3 价值(agent-friendly debug)

- LLM agent 拿到一个 capability:问 `provenance()`,立刻知道完整故事
- 调试 "为什么这个进程有这 cap" 不需要 trace syscall log
- 类似 git blame,但 for capabilities

### 5.4 wire format + Confidence + DAG 扩展

- § 5.1 ProvenanceInfo 是 jhyy-side struct(7 字段);wire format 定义在扩展 spec
- **扩展 spec**: [`v0.0.4-debug-abi.md`](v0.0.4-debug-abi.md) § 4 + § 7(2026-08-12 起草并 🔒 锁定,Q-Compiler-007 已闭环 per D41)
  - **§ 4 Confidence 三级标记**: `HardFact / CompilerInjected / Heuristic`,每个字段单独标,LLM agent 据此判断 trust level
  - **§ 7 DAG 增强**: 现有 `grant_chain: *ProvenanceInfo`(NULL 结尾单向链)→ 加 `parents:[u32;8] + children:[u32;8]`,表达 multiparent derive(add-only,向后兼容)
  - **§ 7.3 尺寸**: 加 DAG 后 jhyy 侧与 wire-format 均 **136B**
- **interface name 不动**(per D14 `Cap::provenance()`);字段类型部分见上方 D40 修订说明

### 5.5 性能成本

- debug build:每个 cap 操作多一次 table lookup + update → 可接受(debug 慢一点)
- release build:strip 后零成本
- L1-L2-L3 检查不依赖 provenance(provenance 是 debug-only metadata)

## § 6 Layered TCB(2026-08-04 锁)

**3 层 trust anchor**:

| 层 | 实现位置 | 检查内容 | 失败模式 |
|---|---------|---------|---------|
| **L1 编译器** | `jhyy compile` | 类型规则 / phantom / `as` 拒绝 / `unsafe_cap` 警告 | 编译错误(fail-loud) |
| **L2 Runtime** | process startup + capability table | `WaiverCap` bit / waiver 路径合法性 | 运行期 abort(fail-fast) |
| **L3 Kernel** | syscall handler | cnode 实际检查 / rights bitmask | syscall 错误(fail-safe) |

**设计原则**:
- L1 拒掉的 → 永不执行(早失败,无运行期成本)
- L2 兜 L1 漏的 → 运行期优雅降级
- L3 是 ground truth → syscall 真执行前的最后检查

**与 Narrow Waivers 关系**:
- Narrow Waivers = L2 的具体实现机制(用 WaiverCap privilege)
- Layered TCB = L1 + L2 + L3 的总体框架
- 两者搭配 = 编译期强 + 运行期兜的双层防御
