## § 1 现有架构对 GUI 的接触面 🔒/🧪

### 1.1 已锁的"天生 GUI 友好"部分 🔒

| 架构决策 | GUI 接触面 | 友好度 |
|---------|-----------|--------|
| **微内核** | GUI compositor 在用户态,kernel 不管合成 | ⭐⭐⭐ Wayland 同构 |
| **capability-based** | `Cap<Surface>` / `Cap<Compositor>` / `Cap<Seat>` = 天然权限边界 | ⭐⭐⭐ Wayland 用 fd,我们用 cap 更强 |
| **Type-driven IPC** | GUI protocol 编译期验证(handler 签名 + 字段访问) | ⭐⭐⭐ buffer overrun 编译期消除 |
| **endpoint namespace** | 每个 GUI app 独立的 endpoint → 输入事件路由 | ⭐⭐⭐ 跟 Wayland wl_resource 类似 |
| **hybrid 内存模型** | framebuffer = raw MMIO + volatile;GUI 状态 = region types;共享 surface = `unsafe_share` | ⭐⭐⭐ 完美对齐 GUI 内存需求 |
| **编译期 provenance** | GUI app debug("谁的 surface 显示错了"一行 walk 回根因) | ⭐⭐⭐ GUI bug 90% 是异步 + 多进程,传统 debugger 抓不到 |
| **walkable error chain** | 渲染失败 → walk 回资源创建点 | ⭐⭐⭐ |
| **5 原则 #5** kernel 不解决语言问题 | compositor / widget 库 / 字体渲染全在用户态 | ⭐⭐⭐ |
| **5 原则 #4** debug 在语言里 | GUI bug 编译期消除 + 类型化状态 | ⭐⭐⭐ **最大利好** |
| **boot 路径 UEFI + GOP** | M1 启动就拿到 framebuffer;M8a 已经规划 persistent | ⭐⭐⭐ 第一步不用从零搞起 |

**结论**:架构选型已经把 GUI 友好的基础锁了。GUI 是**纯增量**(新里程碑 + spec 增补),不需要回头改 M1-M11 任何决策。

### 1.2 潜在阻碍 🧪

| 阻碍 | 何时解锁 | GUI 影响 |
|------|---------|---------|
| MVP 不用 generics (`Vec<T>`) | sprint 3i (v3.2+) | GUI widget 库需要动态布局 |
| MVP 不用 closures | sprint 3j (v3.2+) | GUI 事件 handler 大两用 `\|event\| ...` |
| MVP 不用 std lib | sprint 3l (v3.2+) | GUI 工具包(egui / 类似)需要 std |
| MVP 不用浮点 | sprint 3h (v3.2+) | 字体抗锯齿 / 3D / 渐变需要 f32/f64 |
| **GPU driver 完全没规划** | ⏳ M12+ 探索 | **现代 GUI 最大阻塞** |
| 输入事件 dispatch 协议无 spec | M8d 时起草 | 键盘 + 鼠标 + 触摸事件路由 |

### 1.3 GUI 跟 jhyy 编译器的双向关系 🧪

**正向(GUI → compiler)**:
- GUI 字体抗锯齿 = 需要浮点 → 加速 sprint 3h
- GUI widget 库 = `Widget<T>` / `Container<Child>` = 需要 generics → 加速 sprint 3i
- GUI 事件 handler = `on_click(\|event\| ...)` = 需要 closures → 加速 sprint 3j
- GUI 工具包 = 需要 std lib → 加速 sprint 3l

**反向(compiler → GUI)**:
- Type-driven IPC = GUI protocol 编译期验证
- capability provenance = GUI app debug
- 错误链 walkable = 渲染失败根因追踪
- 5 原则 #4 "Debug 在语言里" = GUI bug 编译期消除

**双向循环**:
- jhyy 编译器自身就需要 GUI(regress.py / 测试 runner / IDE / debugger front-end 全是 GUI)
- 如果 GUI 推后到 M11,jhyy 编译器自身也没 GUI 工具
- **GUI 同时加速 jhyy 编译器特性 + 给 jhyy_OS 应用层**

## § 2 6 个 GUI 架构 macro-strategies 🧪

### 2.1 A. Wayland-style(microkernel + capability + IPC)🧪 ✅ 推荐

**理念**: 每个 GUI app = 独立进程,持有 `Cap<Surface>`,compositor 进程合成 surface 到屏幕;输入事件通过 IPC 路由。

| 项 | 内容 |
|---|------|
| **好处** | 完美匹配 jhyy_OS 现有架构(microkernel + cap + IPC);每个 GUI app 沙箱化;sway/wlroots 实现可参考 |
| **坏处** | 协议设计要严谨(type-driven IPC 帮我们);需要 compositor 进程(新里程碑);首次启动稍慢(进程间 IPC 初始化) |
| **类比** | Wayland / Redox / SerenityOS |
| **MVP 适用** | ✅ **推荐**(架构同构,改动最小) |
| **何时启用** | M8a 真做时 → M8d compositor → M8e 输入协议 → M12 GUI 工具包 |

### 2.2 B. X11-style(client-server + X protocol)❌

**理念**: X server 集中管理输入 + 输出,GUI app 是 X client 走 X protocol。

| 项 | 内容 |
|---|------|
| **好处** | 远程显示天然支持;成熟 |
| **坏处** | X protocol 1987 年遗留(2D 绘图为主,扩展性差);没有 capability 概念,安全靠 ACL;sway 时代 Wayland 已成事实标准 |
| **MVP 适用** | ❌ 不适合(违反"可行且简单"原则)— X11 是 legacy,不应再走 |
| **何时启用** | 不启用 |

### 2.3 C. Android-style(SurfaceFlinger + Binder IPC)🧪

**理念**: 每个 app = Java VM 进程,通过 Binder IPC 跟 SystemServer 通信;SurfaceFlinger 合成。

| 项 | 内容 |
|---|------|
| **好处** | 现代 Android 验证;每 app 一个进程隔离 |
| **坏处** | 需要 Java/ART(我们用 jhyy)— Binder 协议复杂;依赖重度运行时 |
| **MVP 适用** | ❌ 不适合(语言不匹配) |
| **何时启用** | 不启用(jhyy 不用 Java) |

### 2.4 D. iOS/macOS-style(单一应用 + 私有 surface)🧪

**理念**: 系统合成器管所有 surface,app 提交 layer;event 由系统分发。

| 项 | 内容 |
|---|------|
| **好处** | UX 流畅(动画 / 转场原生支持) |
| **坏处** | 闭源参考少;EventKit / CoreAnimation 太复杂 |
| **MVP 适用** | ⏳ **部分可借鉴**(surface 模型 OK,event 分发可简化) |
| **何时启用** | M8d compositor 设计时参考 layer 模型 |

### 2.5 E. Plan 9-style(everything is a file + 9P)🧪

**理念**: 窗口 / 输入设备 / 网络都是文件,9P 协议统一访问。

| 项 | 内容 |
|---|------|
| **好处** | 概念统一(RIO 远程文件很美) |
| **坏处** | 9P 协议设计要重新规划;没有 native capability;UX 慢(每次交互 9P round-trip) |
| **MVP 适用** | ❌ 不适合(违反"可行且简单"原则)— 9P 已被 M7 锁的自研 FS 协议替代 |
| **何时启用** | 不启用 |

### 2.6 F. 自研 minimum(framebuffer + 单 app)🧪

**理念**: 不做 compositor,每个 app 直接画 framebuffer;kernel 调度谁画。

| 项 | 内容 |
|---|------|
| **好处** | 极简(M1 就能做)— 不需要 IPC / capability / 合成协议 |
| **坏处** | 只能单 app;没有窗口系统;没有输入路由;现代 GUI 不可能 |
| **MVP 适用** | ✅ M8a 早期 UI(boot phase keyboard + 简单 console)— **但仅限 M8a 阶段** |
| **何时启用** | M8a 用 F;M8d 切换到 A |

### 2.7 6 个 strategy 选取

| Strategy | M8a 早期 UI | M8d / M12 完整 GUI |
|----------|------------|---------------------|
| A Wayland-style | ❌ 太重 | ✅ **推荐** |
| B X11-style | ❌ | ❌ |
| C Android-style | ❌ | ❌ |
| D iOS-style | 🧪 部分借鉴(layer 模型) | 🧪 部分借鉴 |
| E Plan 9-style | ❌ | ❌ |
| F 自研 minimum | ✅ M8a 早期 | ❌ 切换到 A |

**结论**: M8a 走 F(极简);M8d / M12 完整 GUI 走 A(Wayland-style + jhyy capability 增强);D 部分借鉴 surface / layer 模型。

## § 3 M8d / M12 集群候选 milestone 拆分 🧪

### 3.1 候选 A:把 GUI 全部塞进 M8a 扩展(M8a' + M8d)

| 候选 milestone | 目标 | 编译器侧硬前置 |
|---------------|------|--------------|
| **M8a** (现有) | framebuffer paint + boot-phase keyboard + 简单 console | M1 + 3c(volatile MMIO)|
| **M8a'** | framebuffer persistent + 简单 widget(按钮 / 文本 / 输入框) | M8a + 3h 浮点(抗锯齿)|
| **M8d** (新) | compositor 进程 + Wayland-style surface protocol + 输入事件路由 | M8a' + M4 (capability) + M5b (IPC) + sprint 3g (3g.5 phantom)|

**好处**: M8 集群自包含,不污染 M1-M11 主链
**坏处**: M8a' / M8d 都要 sprint 3h(浮点)— 拉前 sprint 3h 优先级

### 3.2 候选 B:独立 M12 GUI milestone(在 M11 之后)

| 候选 milestone | 目标 | 编译器侧硬前置 |
|---------------|------|--------------|
| **M12** (新) | 完整 GUI 系统(compositor + window system + GUI 工具包 + 输入协议 + GPU driver 可选)| M11 + sprint 3h + sprint 3i + sprint 3j + sprint 3l |

**好处**: M1-M11 主链不被 GUI 阻塞;M12 可以吃满 std lib + generics + closures
**坏处**: GUI 推后到 M11 之后 — M11 之前 jhyy_OS 没 GUI,jhyy 编译器也没 GUI 工具

### 3.3 候选 C:两阶段(M8d compositor 基础 + M12 GUI 工具包)

| 候选 milestone | 目标 | 编译器侧硬前置 |
|---------------|------|--------------|
| **M8d** (新,在 M8c 之后)| **compositor + Wayland surface protocol + 输入事件路由**(协议层)| M8c + M4 + M5b + 3g |
| **M9 / M10** | 现有(不变)| — |
| **M11** | 现有(不变)| — |
| **M12** (新)| **GUI 工具包 + widget 库 + 字体 + GPU driver 可选**(应用层)| M11 + 3h + 3i + 3j + 3l |

**好处**:
- M8d 拿协议骨架(M5b 之后立刻能做)— jhyy 编译器能写 GUI 协议测试
- M12 拿 GUI 工具包(M11 后)— jhyy 编译器自己能用 GUI 工具
- 阶段清晰:协议层(M8d)跟应用层(M12)分离

**坏处**: M8d 在 M5b 之后,但 3g 在 M3-M4 之间,M8d 实际可用要等 3g.5 + 3g.7 完成

### 3.4 候选 D:跟 M11 集成(M11 = 自举 OS 跑 jhyy 编译器,jhyy 编译器自带 GUI)

| 候选 milestone | 目标 | 编译器侧硬前置 |
|---------------|------|--------------|
| **M11** (改) | 自举 OS 跑 jhyy 编译器 + jhyy 编译器自带 GUI 工具(regress / IDE / debugger)| 现有 M11 依赖 + 3h + 3i + 3j + 3l + GUI 协议 spec |

**好处**: M11 一举多得(自举 + GUI)— 跟"双线作战"原则契合
**坏处**: M11 范围爆炸(原 M11 已经够重)— 可能推迟 M11 收尾

### 3.5 4 个候选比较

| 维度 | A(M8a' + M8d) | B(M12 独立) | C(M8d + M12 两阶段)| D(集成 M11) |
|------|---------------|-------------|---------------------|--------------|
| M1-M11 主链阻塞 | 拉前 sprint 3h | 不阻塞 | M8d 在 M5b 后 | M11 范围爆炸 |
| jhyy 编译器获 GUI | M8d 末(协议) | M12 末 | M8d 末(协议) + M12 末(工具)| M11 末 |
| jhyy_OS 用户获 GUI | M8d 末 | M12 末 | M8d 末(协议) + M12 末(工具)| M11 末 |
| 复杂度 | 中 | 低 | 中 | 高 |
| 跟 5 原则契合 | ✅ | ✅ | ✅ **推荐** | ✅ 但范围爆炸 |

### 3.6 关键观察

- **架构不阻塞任何候选** — 4 个候选都能在现有 M1-M11 基础上做
- **最关键的决策点是"什么时候用户能用上第一个 GUI 应用"**
- M8a 阶段(用 F 策略)= 只能 framebuffer paint + 简单 console(boot screen 类)
- M8d 阶段(用 A 策略)= 协议层就位,但 GUI 工具包要等 generics + closures
- M12 阶段(用 C 策略)= GUI 工具包就位,jhyy 编译器自身能用
- **推荐候选 C** — 阶段清晰,跟"双线作战"原则契合,jhyy 编译器早期能写 GUI 协议测试

## § 4 Wayland-style surface protocol 草案 🧪

> 借用 Wayland 核心概念,但用 jhyy capability 替代 fd。**这是协议骨架,不是 spec**。

### 4.1 核心 cap 类型

| Cap 类型 | 持有者能做什么 |
|---------|--------------|
| `Cap<Compositor>` | 提交 surface 列表给合成器;接收显示配置变更通知 |
| `Cap<Surface>` | 提交 buffer 到 surface;设置 surface 角色(toplevel / popup / subsurface);接收 enter/leave 事件 |
| `Cap<Buffer>` | 共享 framebuffer 引用(shm / dmabuf);持有者可以读写像素 |
| `Cap<Seat>` | 持有 = 访问输入设备;接收 keyboard / pointer / touch 事件 |
| `Cap<Output>` | 描述物理屏幕(分辨率 / 刷新率);持有者可以查询 |

### 4.2 协议消息类型(Type-driven IPC 编译期验证)

```jhyy
// compositor protocol
type SurfaceCommitMsg = struct {
    surface: Cap<Surface>,
    buffer: Cap<Buffer>,
    damage: [Rect; 16],          // 重绘区域(限制 16 块)
};

type CompositorConfigMsg = struct {
    output: Cap<Output>,
    mode: DisplayMode,
};

// input protocol
type KeyboardKeyMsg = struct {
    seat: Cap<Seat>,
    keycode: u32,
    state: KeyState,             // Pressed / Released
    modifiers: ModifierSet,
};

type PointerMotionMsg = struct {
    seat: Cap<Seat>,
    surface: Cap<Surface>,
    x: u32,
    y: u32,
};

// surface lifecycle
type SurfaceDestroyMsg = struct {
    surface: Cap<Surface>,
};
```

### 4.3 进程模型

```
┌─────────────────────────────────────────────────────────┐
│                    Compositor 进程                       │
│  - 持有 root Cap<Compositor> + Cap<Output>               │
│  - 接收所有 surface commit                                │
│  - 合成 surface 到屏幕                                    │
│  - 路由输入事件到对应 surface 持有者                       │
└─────────────────┬───────────────────┬───────────────────┘
                  │ IPC               │ IPC
                  ▼                   ▼
        ┌──────────────────┐  ┌──────────────────┐
        │  GUI App 进程 A  │  │  GUI App 进程 B  │
        │  - Cap<Surface>  │  │  - Cap<Surface>  │
        │  - Cap<Buffer>   │  │  - Cap<Buffer>   │
        │  - Cap<Seat>     │  │  - Cap<Seat>     │
        │  - widget 渲染   │  │  - 文本渲染      │
        └──────────────────┘  └──────────────────┘
```

### 4.4 跟 Wayland 的差异

| Wayland | jhyy_OS Wayland-style |
|---------|----------------------|
| wl_display (fd) | `Cap<Compositor>` (8 字节 + phantom) |
| wl_resource (id) | `Cap<Surface>` / `Cap<Seat>` / `Cap<Buffer>` |
| `wl_registry.bind()` | `cap_grant()` + endpoint IPC |
| XWayland 兼容层 | ⏳ M12+ 视情况(可能不实现,纯 native Wayland 风格) |
| zwp_linux_dmabuf_v1 | ⏳ GPU 加速时再加(M12 末或 post-M12) |

**好处**: Wayland 工具(weston / sway / wlroots)可以**参考实现**,但不直接复用(协议层对得上,实现语言不同)

### 4.5 关键设计决策(待 M8d 实施时锁)

| # | 决策 | 默认假设 |
|---|------|---------|
| 1 | shm buffer(`mmap` 共享)vs dmabuf | M8d 用 shm(简单,M12 末再考虑 dmabuf / GPU) |
| 2 | 输入事件 pull(轮询)vs push(中断)| push(input 中断 → compositor IPC → 目标 app)|
| 3 | 子 surface(嵌套窗口)| M12 末再加 |
| 4 | 动画 / 转场 | M12+ 探索 |
| 5 | 屏幕阅读 / 无障碍 | post-M12 |

## § 5 MVP 限制 vs 现实限制 🧪

### 5.1 MVP(M1-M10)能做的"够用 GUI"

**能**:
- 单进程 framebuffer 应用(直接画像素,不合成)
- 简单 widget(button / text / input box)
- PS/2 keyboard 输入(M8b)
- boot screen / 简单 console(M8a 已规划)

**不能**(受 MVP coding style 限制):
- 动态布局(`Vec<Widget>`)— sprint 3i
- 闭包事件 handler(`on_click(|e| ...)`)— sprint 3j
- std GUI lib(egui / 类似)— sprint 3l
- GPU 加速 — **完全没规划**
- 鼠标 / 触摸 — M8b 只有 PS/2 keyboard

**结论**: MVP 阶段的 GUI 只能做"自绘像素 + 简单 widget + 键盘输入",够 demo,不够实用。

### 5.2 现代 GUI(多窗口 + 合成 + GPU 加速 + 闭包事件)需要等

| 需求 | 编译器特性 | milestone |
|------|-----------|-----------|
| 动态布局 | generics (3i) | M11 之前可推前(per D28 调整)|
| 闭包事件 | closures (3j) | M11 之前可推前 |
| std GUI lib | std lib (3l) | M11 |
| 字体抗锯齿 | 浮点 (3h) | M8a' 时推前 |
| GPU 加速 | GPU driver + sprint 3h 浮点 | **M12+ 完全新** |

### 5.3 sprint 推前 vs 不推前的权衡 🔒 → D33

per coordination § 3 D28:
- 3h 浮点:"3g.7 后可推(语言便利性,M1 启动后即可)— 但 MVP 内核不用 f32/f64,优先级低"
- 3i generics:"M11 启动前必推"
- 3j closures:"M11 启动前必推"
- 3l std lib:"M11 启动前必推"

**两种路线**:

| 路线 | 描述 | 影响 |
|------|------|------|
| **A. 推前 3h/3i/3j** | 3h 推 M8a',3i/3j 推 M8d 之前 | GUI 早期就吃完整特性;但破坏 compiler sprint 节奏 |
| **B. 不推前 + M8d 单态 type 妥协** 🔒 | M8d 用单态 type(SurfaceRole / SeatRole 各自一份 enum),事件 handler 用 function pointer(非闭包),M12 GUI 工具包吃完整 3h/3i/3j/3l | **D28 不动**;compiler sprint 节奏不被破坏;M8d 协议重复但能跑 |

**🔒 锁 D33**:**选 B 路线,D28 不调整**
- M8a 用整数调色板(无 f32/f64)— 内核传统
- M8d protocol 用单态 type(每个 surface role 一份)— 不依赖 generics
- M8d 事件 handler 用 function pointer — 不依赖 closures
- M12 GUI 工具包直接吃完整 3h(抗锯齿字体)+ 3i(Widget<T>)+ 3j(闭包事件)+ 3l(std GUI lib)
- **OS 团队不需要靠"推前 compiler sprint"来解锁 GUI**

**代价**:
- M8d protocol 代码量增加(N 个 surface role × N 个 message type)— 但每个 role 几十行,总 < 1k 行
- M12 GUI 工具包必须等 M11(3i+3j+3l 都在 M11)— 这跟 GUI 工具包本来就在 M12 一致,无新阻塞

## § 6 GPU 加速问题(可能最大的阻塞点)🧪

### 6.1 为什么 GPU 难

| 难点 | 详情 |
|------|------|
| **driver 协议复杂** | 现代 GPU(drm / i915 / amdgpu)driver 上万行;shader 编译(Vulkan / OpenGL / Metal)要 spec 几百页 |
| **硬件依赖** | 不同 GPU vendor 协议不同(Intel / AMD / Nvidia / ARM Mali);QEMU virtio-gpu 是简化路径但性能差 |
| **spec 复杂度** | Vulkan 1.3 spec ~1000 页;OpenGL ~3000 页;我们 MVP 不能复制这些 |
| **MVP 不需要** | M1-M10 不需要 GPU(boot / IPC / cap 都不需要)— 但 M8d GUI 立刻需要 |

### 6.2 候选路径

| 路径 | 复杂度 | 何时启用 |
|------|--------|---------|
| **A. 不做 GPU,只用 CPU 合成** | 低 | M8d 直接上 — compositor 在 CPU 上 blend / scale,sway 早期模式 |
| **B. virtio-gpu(只 QEMU)** | 中 | M8d + QEMU 测试,实机不支持 |
| **C. 自研最小 GPU API(Vulkan subset)** | 极高 | post-M12 |
| **D. 借用 mesa / 借用项目** | 中(但污染"纯 jhyy from day 1"原则) | ❌ 不考虑 |

### 6.3 推荐路径

**M8d / M12 走 A(纯 CPU 合成)**:
- compositor 在 CPU 上 blend surface(skia / 自研 CPU 实现)
- 性能够 demo + 简单应用(60 FPS @ 1080p skia 软渲染 = 可接受)
- 现代 GPU 留给 post-M12

**M12+ 探索路径**:
- 评估 virtio-gpu(简化 DRM 子集)— 如果性能瓶颈显现
- 不做通用 Vulkan / OpenGL(违反"可行且简单")

### 6.4 CPU 合成 vs GPU 合成的 trade-off

| 维度 | CPU 合成 | GPU 合成 |
|------|---------|---------|
| 复杂度 | 低(几百行 blend 代码) | 极高(整个 GPU driver + shader 编译) |
| 性能 | 60 FPS @ 1080p ~单核 50% | 60 FPS @ 4K 多 surface ~ 5% |
| 兼容性 | 所有硬件 | 需要 GPU driver |
| 适合场景 | M8d / M12 早期 | post-M12 高分屏 / 3D |

## § 7 输入事件模型(键盘 / 鼠标 / 触摸)🧪

### 7.1 现有规划

M8a: SimpleTextInput(post-boot flag)— boot 阶段键盘能用,boot services 退出后失效
M8b: PS/2 keyboard 真 driver — 普通键盘

### 7.2 缺口

| 输入设备 | 现有 | 缺口 |
|---------|------|------|
| 键盘 (PS/2) | ✅ M8b | 无 |
| 鼠标 (PS/2) | ❌ | M8b 加上(便宜) |
| 触摸 (USB / I2C) | ❌ | M8b 末或 M12 |
| 触控板 (I2C) | ❌ | post-M12 |
| 游戏手柄 | ❌ | post-M12 |

### 7.3 输入事件路由

```
硬件中断(PS/2 / USB HID)
    ↓
input driver(内核 / M6)
    ↓
seat 抽象(`Cap<Seat>` = 输入设备集合)
    ↓
compositor 进程(根据 surface 焦点路由)
    ↓
目标 GUI app(Cap<Surface> 焦点持有者)
    ↓
widget 事件处理(sprint 3j 闭包)
```

### 7.4 输入事件协议草案

```jhyy
// per-seat 事件
type SeatEventMsg = struct {
    seat: Cap<Seat>,
    event: SeatEvent,            // enum KeyboardKey / PointerMotion / TouchDown / ...
};

// 焦点跟踪(由 compositor 管)
type SurfaceFocusMsg = struct {
    surface: Cap<Surface>,
    seat: Cap<Seat>,
    serial: u64,                 // 事件序列号,防止 stale 事件
};
```

### 7.5 关键设计决策

| # | 决策 | 默认 |
|---|------|------|
| 1 | 键盘 repeat(长按重复)| M8d 加(简单 timer + 重复 send)|
| 2 | IME(输入法) | post-M12(需要 std GUI lib + 国际化) |
| 3 | 手势识别 | post-M12(需要算法 + calibration) |
| 4 | 多 pointer / 多 touch | M8d 末(简单)— 每个 pointer 一个 id |

## § 8 jhyy 编译器自身的 GUI 需求 🧪

### 8.1 现况

jhyy 编译器自身目前**无 GUI**:
- regress.py 是命令行
- `jhyy.exe` 是 CLI
- spec / ABI / roadmap 全是 markdown

### 8.2 哪些 GUI 工具最受益

| 工具 | GUI 收益 | 优先级 |
|------|---------|--------|
| **IDE** (syntax 高亮 / autocompletion / jump-to-def) | ⭐⭐⭐⭐⭐ | 高 |
| **regress runner** (47/47 test 可视化) | ⭐⭐⭐⭐ | 中 |
| **debugger front-end** (cap provenance 可视化) | ⭐⭐⭐⭐⭐ | 高(原则 4) |
| **type error walker** (错误链 GUI walk) | ⭐⭐⭐⭐⭐ | 高(原则 4 + agent-friendly) |
| **profiler** (codegen pass 时间分布) | ⭐⭐⭐ | 低 |

### 8.3 GUI 让 jhyy 编译器受益的反向链路

- **type error walker GUI** = 编译期错误的可视化探索 → **直接推动 L4 Capability query API**(per v0.0.3-explorations § 6.1)
- **debugger front-end** = cap provenance + walkable error chain 的可视化 → **直接推动 jhyy OS 调试工具**
- **regress runner** = 47/47 测试的可视化 → **推动 v1.0 闭环回归预期可视化**(12 OK 持平 vs 47/47 全过的 GUI 直观差异)

### 8.4 关键观察

- **GUI 不只是 jhyy_OS 用户的需求,也是 jhyy 编译器自身的工具需求**
- 这正是"双线作战"原则的另一红利:不是两个项目抢资源,是**互相喂养**
- GUI 一来,jhyy 编译器的内部工具链 + jhyy_OS 应用层**同时获益**

### 9.1 风险矩阵

| 风险 | 严重度 | 缓解 |

| 闭包事件 handler 写错 | 低 | Q-Compiler-003 / D20 attribute 已解决 |
| sandbox 漏洞(app 拿到其他 app surface) | 中 | capability 类型系统保证;Type-driven IPC 编译期验证 |

### 9.2 跟 5 原则契合度

| 原则 | 契合度 | 备注 |
|------|--------|------|

- 不改 5 原则
