### 1.1 Framing 校准:缺 feature ≠ blocker

User 2026-08-04: "没有，可以没有，只要不冲突都可以加嘛，jhyycompiler也是一个相当年轻的项目"

- **旧 framing(我之前用的,错)**: "MVP 不能用 `Vec\<T\>` 因为 jhyy 没有 generics → MVP 受限"
- **正确 framing**: "MVP 暂时不需要 `Vec\<T\>`(用 `[T; N]` 固定数组足够);如果未来需要,加 generics 到 jhyy,只要不跟现有设计冲突即可"
- jhyy 是 OS 驱动设计:OS 需求 → 反向驱动 jhyy 加 feature
- 唯一硬约束:**不冲突**——不破坏 ABI v1.0.0、不破坏 lang-spec v1.x 已锁章节
- 例:`generics` 加到 jhyy = 纯编译期(单态化),不影响 ABI → 0 冲突
- 例:`closures` 加到 jhyy = 编译期闭包结构体展开,ABI 加几条 fn ptr 约定 → 不冲突
- 例:加 `async` = 当前 ABI 加 task 帧布局 → 需评估,但理论可加

详见 memory `feedback_jhyy_extensible.md`

| 控制流 | if-else / while / for / break / continue / return / match(含穷尽性检查 § 11.3)|
| 函数 | 顶层 fn + 递归 + 多参数 + struct sret |

### 2.2 ABI 关键事实(v1.0.0 锁)

来源: [`jhyy-abi-v1.0.0.md`](../../JiHuiYiYou/docs/abis/jhyy-abi-v1.0.0.md)

- 目标: **amd64_win only**(无 ELF / Linux)— OS 引导路径必须 EFI+PE/COFF
- 调用约定: 继承 MS x64(RCX/RDX/R8/R9 + 栈)
- struct pass-by-value: **JHYY 自有约定**(调用方栈拷贝 + 逐字段复制),与 Windows ABI 不兼容 → 跨 FFI 不可传 struct
- struct return: 调用方分配返回槽,作隐式第一参数
- `*T` = 8 字节,`[*]T` = 16 字节(ptr + len)
- 名称修饰: `$name`;extern fn 原名(无 $)

## § 3 锁定决策(spec 校准后)

### 3.1 五原则(v0.0.0 § 2 已锁,本 doc 仅引用)

1. 可行且简单
2. 双线作战是核心优势
3. 项目初期寄生 Windows
4. Debug 在语言里,不靠 gdb
5. Kernel 绝不解决语言应该解决的问题

### 3.2 内存模型(hybrid,region types primary)

| 对象类别 | 内存机制 | 理由 |
|---------|---------|------|
| **Cap** | linear types(单 owner,move/revoke)| 不可复制,显式 grant |
| **用户数据** | **region types(primary)** | jhyy 编译器自身用 arena.jhyy,语言层原生支持 |
| **kernel 临时** | region types | 短生命周期 |
| **硬件 MMIO** | raw pointer + volatile | 必须 bypass 类型系统(sprint 3c volatile)|
| **跨进程共享** | `unsafe_share` privilege bit | 单 bit 运行期门控 |

**明确 DROP**:
- borrow checker as primary(违反 § 3.1 原则 1 — 编译器本身就不用 borrow checker,OS 为何要?)
- 全 RAII(lang-spec 不支持)
- 全 GC(spec 不支持,引入即违反 § 3.1 原则 5)

### 3.3 Narrow Waivers 设计(v0.0.1-capability.md 待增)

来源: 会话 2026-08-04 共识

- 99% capability 检查 = 编译期(cap_constructor 白名单 + phantom type + 不可降级)
- 1% 特例 = 显式 `unsafe_cap { ... }` 块(必须 unsafe block)
- `WaiverCap` privilege = 进程 capability 表的 single bit
- Layered TCB: 编译器(主)+ runtime waiver(兜底)

### 3.4 Debug by design(v0.0.0 § 2 原则 4 + 设计 doc 待增)

- 编译期消除 bug 类(类型驱动 IPC + capability provenance)
- 错误链 walkable(`Result::Err(prev: *Err, code: ErrCode)`)
- 类型化内核状态(`KernelState` enum,debug build 带历史)
- Capability query API(`Cap::provenance() -> DebugInfo`)

## § 5 MVP boot 路径修订(2026-08-04)

### 5.1 之前假设

```
jhyy 编 multiboot2 ELF → QEMU -kernel multiboot2.bin
```

需要 v2.x 重写 QBE ELF 后端(**阻塞**)

### 5.2 修订后(UEFI + PE/COFF)

```
jhyy 编 kernel.efi (PE/COFF) → QEMU -bios OVMF -kernel kernel.efi
```

**好处**:
- **不需要** QBE ELF 后端 — 用现成的 amd64_win QBE 目标
- OVMF(QEMU 的 UEFI firmware)原生支持 PE/COFF,直接 boot
- 实机 boot 同路径(USB EFI 应用)
- UEFI = v0.0.0 已锁选项,无矛盾

**boot stub 需求**(仍需 sprint 3a-3f,但**绝大多数不需要 inline asm**):
- ~~real mode → protected mode → long mode 切换~~ ❌ — **2026-08-04 spike 验掉**:UEFI x64 固件交接时已在 long mode、分页已开,**无模式切换**。把 EFI SystemTable 走 MS x64 约定的函数指针(EFIAPI = MS x64)直接调即可,`extern fn` 够用
- 页表建立(asm + volatile,sprint 3a-3f 需要)
- framebuffer 获取:**UEFI GOP 走 EFI 函数指针**(BootServices->LocateProtocol + GOP->Mode->FrameBufferBase),不需要 asm syscall-like
- 跳入 kernel entry(asm + link_section,sprint 3a/3e 需要)

**spike 详情**(2026-08-04):见 `spike/boot.s` + `spike/wrap_gpt.py`(GPT 包裹镜像)+ `spike/startup.nsh`(诊断)。最小验证:`EFIAPI efi_main(ImageHandle, ST)` 走 MS x64(注意 **RCX=ImageHandle,RDX=SystemTable**,不是 RCX=ST),`ConOut->OutputString` 走 `[protocol + 8]`(注意 **RCX=*This**,不是 auto),isa-debug-exit port 0xf4 → QEMU exit code = (byte << 1) | 1。QEMU 跑命令:`qemu-system-x86_64 -drive if=pflash,format=raw,readonly=on,file=$OVMF -drive file=fat:rw:esp_root -device isa-debug-exit,iobase=0xf4,iosize=1`(注意用 `fat:目录` 后端,比 GPT 镜像省事)。

详见 memory `feedback_uefi_x64_conventions.md`。

### 5.3 双引导路径(并列选项)

| 路径 | 何时用 | 何时解锁 |
|------|--------|---------|
| **UEFI + PE/COFF**(默认) | MVP(M1+)| M1 时已可用 |
| **Multiboot2 + ELF** | 实机 legacy BIOS / 自定义 bootloader | v2.x QBE ELF 后端完成后 |

MVP 锁定 UEFI 路径,ELF 路径留 v3.x+ 视情况启用。

## § 6 MVP coding style(jhyy v1.x 现实约束下)

### 6.1 折中

| 我之前想象 | spec 约束下折中 |
|----------|----------------|
| `Vec\<T\>` 动态数组 | `[T; N]` 固定数组 + 长度变量(N 是编译期常量,够 MVP 用)|
| 闭包式 IPC handler | `fn handler(msg: Message, env: *Env) -> Reply` + struct env |
| `&mut T` 借用 | `*mut T` raw 指针 + 手动 discipline(sprint 3g 后改 `&mut`)|
| `&T` 共享借用 | `*const T` raw 指针 + 手动 discipline |
| 自动析构 | 显式 `arena_destroy()` / `cap_revoke()` |
| 嵌套 fn | 顶层 fn + 显式 env struct 参数 |

### 6.2 折中"够用吗?"(✓/✗ 分析)

- 固定数组 vs `Vec<T>`: ✓ — MVP 内核不需要动态调整大小,boot/runtime 数据结构都预知大小
- 显式 handler vs 闭包: ✓ — IPC message types 固定,handler 集静态,显式 dispatch table 完全够
- raw 指针 vs `&mut`: ⚠️ **MVP 技术债(2026-08-05 校准)** — M1-M3 OS 代码必须用 `*mut T` raw pointer + 手动 discipline,因为 `&mut + lifetime` 要等 v3.1 sprint 3g(v3.0 末完成、v3.1 启动后才有);sprint 3g 落地 + M4 启动 = OS 代码可以切换到 `&mut`(也意味着 sprint 3g.5 phantom 0-byte + sprint 3g.7 联调都已在 M4 前完成)。**Q-OS-005 假设已撤回**:之前写"M1 起即可用 &mut"是错的,跟 compiler D5 锁的"M1-M10 用 raw pointer;sprint 3g 后改 &mut"冲突
- 手动析构: ✓ — kernel 启动期/进程结束期都是显式控制流点,无 leak 风险
- 无嵌套 fn: ✓ — 顶层 fn + env ptr 显式传,是 C 风格,早就习惯

**MVP M11 能不能编出来?**
- jhyy 编译器自身源里**有** `Vec<T>`、`Map<K,V>`、闭包 visitor(基于 C 编译器架构推断)
- 所以 jhyy OS 跑 jhyy 编译器**必须**先有 sprint 3i + 3j + 3l
- 即 M11 严格排在 3i/3j/3l 之后
- 不是 MVP(M1)的 hard dep,是 M11 的 hard dep
