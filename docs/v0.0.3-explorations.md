## § 1 5 个 macro-strategies 🧪

会话中讨论的 5 个 OS-level 大策略,**择 1-N 个实现**,不是 all-or-nothing。

### 1.1 A. SASOS(Single-Address-Space OS) 🧪

**理念**: 所有进程共享一个虚拟地址空间,no VM isolation,通过 cap 控制访问。

| 项 | 内容 |
|---|------|
| **好处** | IPC 零拷贝(直接传指针);cap 替代 MMU 隔离;kernel 极简 |
| **坏处** | 失去 OS-level 隔离(进程错误直接污染整个地址空间);调试噩梦 |
| **类比** | Inteli/Pi/ASOS、Opal、Berkeley SPIN |
| **MVP 适用** | ❌ 不适合(违反"简单"原则)— MVP 仍 per-process 隔离 |
| **何时启用** | post-M11,作为 ambitious 探索 |

### 1.2 B. 5-Locked Safety 🧪

**理念**: 5 个独立的内存/类型安全锁,组合形成纵深防御。

| # | 锁 | 作用 |
|---|----|----|
| 1 | Cap<T> phantom type | 类型层防伪造 |
| 2 | linear types | cap 单 owner |
| 3 | region types | arena 内存 |
| 4 | raw + volatile | 硬件显式 |
| 5 | unsafe_share privilege | 跨进程显式门控 |

**好处**: 每层独立,缺一个不致命;每层都有 escape hatch(Narrow Waivers)。
**MVP 适用**: ✅ 锁 hybrid 内存模型 + Narrow Waivers。

### 1.3 C. Type-driven IPC 🔒

(已锁,详见 [v0.0.1-syscall-abi.md § 1.1](v0.0.1-syscall-abi.md))

- IPC 消息 = jhyy 类型
- 编译器验证 handler 签名
- 编译期消除一整类 IPC bug

### 1.4 D. Compile-time capability provenance 🔒

(已锁,详见 [v0.0.1-capability.md § 5](v0.0.1-capability.md))

- debug build 每个 Cap 携带 provenance
- 类似 git blame for capabilities
- agent-friendly debug 的核心

### 1.5 E. Continuation kernel 🧪

**理念**: stackless kernel,用 continuation 替代栈。

| 项 | 内容 |
|---|------|
| **好处** | kernel 栈大小固定(无栈溢出);上下文切换 O(1);高并发 |
| **坏处** | 编程模型复杂(continuation passing style);调试困难;性能 trade-off |
| **类比** | Capriccio、kqueue、Squeak VM |
| **MVP 适用** | ❌ 不适合(违反"简单"原则)— MVP 仍传统栈 |
| **何时启用** | post-M11,作为 ambitious 探索 |

### 1.6 5 个 strategy 选取

| Strategy | MVP(M1-M11)| Ambitious(post-M11)|
|----------|-------------|---------------------|
| A SASOS | ❌ | 🧪 探索 |
| B 5-Locked Safety | ✅ 锁 | ➕ 加层 |
| C Type-driven IPC | ✅ 锁 | ➕ 扩协议 |
| D Compile-time provenance | ✅ 锁 | ➕ 加更多 metadata |
| E Continuation kernel | ❌ | 🧪 探索 |

**结论**: MVP 走 B+C+D 三层(锁),A 和 E 留 ambitious 阶段。

## § 2 Build order:Phase 1 Foundation vs Phase 2+ Optimization 🧪

### 2.1 锁定的 Phase 1(M1-M10 Foundation)

按依赖递进:

```
Phase 1 Foundation:
  B (5-Locked Safety) → Cap closure(M4)
  D-lite (Compile-time provenance) → debug support(M5b)
  C (Type-driven IPC) → IPC 协议(M5b-M6)
```

### 2.2 候选 Phase 2+ (post-M11 ambitious)

```
Phase 2+ Optimization:
  A (SASOS) → 共享地址空间探索
  B+ (更多锁) → region-affine / CHERI-style 加固
  C+ (async IPC) → v3.x+ async 集成
  E (Continuation kernel) → stackless kernel
```

### 2.3 优先级

1. **MVP 必须**:B(基础 cap 安全)+ C(type-driven IPC)+ D-lite(provenance)
2. **MVP 可选**:B+(加固)、D+(更细 provenance)
3. **Post-MVP**:A SASOS、E continuation kernel

详见 [v0.0.2-foundation-revision.md § 4](v0.0.2-foundation-revision.md) M1-M11 依赖图。

## § 3 MVP M11 最小集 🧪→🔒

**问题**: M11 = jhyy_OS 跑 jhyy 编译器 + 编译器编 jhyy_OS,需要哪些最小 jhyy/OS 特性?

### 3.1 锁定的最小集(会话共识,2026-08-04)

| # | 必需 | 备注 |
|---|------|------|
| 1 | Lambda Calculus(jhyy 已有)| 基础 |
| 2 | Capability types(Cap<T> phantom)| 8 字节 layout |
| 3 | Linear types(手动 discipline)| MVP 用 explicit grant/revoke |
| 4 | Region types / Arena | jhyy 编译器自身用 arena.jhyy |
| 5 | Memory-only FS(`[u8; N]` 数组)| 不需要泛型 FS |
| 6 | No hardware drivers | QEMU 模拟足够 |
| 7 | UEFI + PE/COFF boot | OVMF |

### 3.2 MVP 不需要(可推迟)

| 不需要 | 推迟到 |
|--------|--------|
| Generics(`Vec<T>` 等)| v3.x sprint 3i |
| Closures | v3.x sprint 3j |

| RAII / destructor | jhyy spec 不支持 |
| Type-driven async IPC | v3.x+ |
| SASOS | post-M11 ambitious |

### 3.3 关键观察

- M1-M10 **不依赖** generics/closures/async
- M11 **依赖** generics/closures(M11 的 jhyy 编译器源用 `Vec<T>` / 闭包 visitor)
- 所以 M11 严格排在 v3.x sprint 3i + 3j 之后

## § 4 Memory model alternatives(已淘汰备选存档)❌

会话中考虑过但被淘汰的内存模型选项。

### 4.1 ❌ Borrow checker as primary

**理由**:
- jhyy 编译器自身用 arena.jhyy(已是 region-based)
- borrow checker 在 region-based memory 上多余(arena 不需要 borrow check)
- 违反"可行且简单"原则(增加编译器复杂度,OS 获益小)
- 见 [v0.0.2-foundation-revision.md § 1.1](v0.0.2-foundation-revision.md) framing 校准

### 4.2 ❌ 全 RAII / 自动析构

**理由**:
- jhyy spec 不支持,需要加 v3.x+ 大特性
- 跟"kernel 永不解决语言问题"原则冲突 — Arena 自动析构应放语言层
- MVP 显式 discipline 够用

### 4.3 ❌ 全 GC

**理由**:
- GC 内核 = 不可接受(kernel 不能 stop the world)
- 用户态 GC 可考虑,但 MVP 不需要
- "kernel 永不解决语言问题"原则

### 4.4 ❌ Reference counting for caps

**理由**:
- cap revoke = 显式语义,refcount 是隐式
- cap 跨进程时 refcount 协议复杂(IPC 时 refcount 怎么走?)
- explicit grant/revoke 更清晰

### 4.5 ❌ CHERI(硬件 capability)

**理由**:
- 需特定硬件,不在 MVP 范围
- 软件 capability + 语言层 Phantom 已经够强

## § 5 Boot path alternatives(已锁定 + 备选)🧪/🔒

### 5.1 🔒 锁定:UEFI + PE/COFF

```jhyy
// 流程
jhyy 编 kernel.efi (PE/COFF)
  → QEMU -bios OVMF -kernel kernel.efi
  → 实机:USB EFI 应用
```

**理由**:
- 复用现有 QBE amd64_win 目标
- OVMF 原生支持 PE/COFF
- 无需 v2.x QBE ELF 重写
- 实机 boot 同路径

### 5.2 ⏳ Multiboot2 + ELF(推迟)

```jhyy
// 流程
jhyy 编 kernel.elf (ELF64)
  → QEMU -kernel kernel.elf(走 multiboot2)
  → GRUB 链
```

**未启用理由**:
- 需 v2.x QBE ELF 后端重写(大特性)
- 实机 BIOS legacy 才有意义(新硬件基本 UEFI)
- MVP 不阻塞

### 5.3 ❌ Custom bootloader(已淘汰)

**理由**:
- 实模式 16-bit 代码用 jhyy 写不现实(无 inline asm 在 16-bit 模式验证)
- 借 C/asm 写 bootloader = 违反"纯 jhyy from day 1"原则
- UEFI stub = 实际等同 custom bootloader,但用 jhyy 写 + UEFI 标准化

## § 6 Debug-by-design 完整展开 🔒

### 6.1 4 层 agent-friendly debug 设计

| 层 | 机制 | 价值 |
|---|------|------|
| **L1 编译期 bug 消除** | 类型驱动 IPC + capability provenance + 类型错误链 | bug 类消除在源头 |
| **L2 类型化错误链** | walkable error chain:`ErrChain { source_loc, prev: *ErrChain, trace: [*]CapId, context: [*]ProvenanceInfo, code }` | agent 顺着 chain 找根因 |
| **L3 类型化内核状态** | `KernelState` enum + history | debug build 携带状态变迁 |
| **L4 Capability query API** | `Cap::provenance()` / `query_caps(pid)` | agent 直接查询 |

### 6.2 为什么 debug 在语言里(不靠 gdb)

- 原则 4(v0.0.0 § 2)— solo developer 不依赖 gdb / kdb / printk
- jhyy 自举 = jhyy_OS 上跑 jhyy 编译器 = jhyy 编译器是 kernel 的 citizen
- debug 工具链也用 jhyy 写,自包含
- LLM agent 友好:类型化状态 = parseable state = agent 可推理

### 6.3 Stretch goal:在 jhyy_OS 上跑 Claude Code

- 不一定实现,但是设计目标
- 需要 jhyy 编译器 + shell + 基础 IO 都在 jhyy_OS 跑通
- Claude Code 跟 jhyy_OS 解耦(只通过 syscall),OS 只需保证 syscall 兼容

## § 7 Narrow Waivers 完整展开 🔒

详见 [v0.0.1-capability.md § 4](v0.0.1-capability.md),本节补充 trigger 场景。

### 7.1 trigger 场景(何时需要 waiver)

| 场景 | 为什么需要 waiver |
|------|-----------------|
| Legacy 互操作(对接老 C 库)| 老库只接 `int fd`,必须 `into_raw()` |
| 硬件直接访问(MMIO)| 必须 raw pointer + volatile |
| Kernel 模块加载(dynamic)| 必须打破 cap 类型边界 |
| 用户特殊需求(自己要求降级)| 显式 self-override |

### 7.2 WaiverCap 获取方式

- 默认 = false
- Kernel 显式 grant(类似 setuid)— 比如 console service、debug service
- 程序自请求 → kernel 验证后才 grant
- revoke = kernel 显式

### 7.3 不滥用 waiver 的约束

- waiver 是 **opt-in**(默认 false),不 opt-in 不能用
- waiver 路径触发后,provenance 记录"waiver used at X"
- linter 可统计项目里 waiver 次数,过多 → 设计问题

## § 8 Layered TCB 完整展开 🔒

### 8.1 3 层 trust anchor

| 层 | 实现位置 | 检查内容 | 失败模式 |
|---|---------|---------|---------|
| L1 编译器 | `jhyy compile` | 类型规则 / phantom / `as` 拒绝 / `unsafe_cap` 警告 | 编译错误(fail-loud) |
| L2 Runtime | process startup + capability table | `WaiverCap` bit / waiver 路径合法性 | 运行期 abort(fail-fast) |
| L3 Kernel | syscall handler | cnode 实际检查 / rights bitmask | syscall 错误(fail-safe) |

### 8.2 设计原则

- **L1 拒掉的 → 永不执行**(早失败,无运行期成本)
- **L2 兜 L1 漏的 → 运行期优雅降级**
- **L3 是 ground truth → syscall 真执行前的最后检查**

### 8.3 失败模式优先级

```
fail-loud (L1) > fail-fast (L2) > fail-safe (L3)
```

- 编译错误 > 运行期 abort > syscall 错误
- 越早失败越好(节省运行期成本,bug 修复便宜)

### 8.4 类比

| 项目 | TCB 设计 | 类比 |
|------|---------|------|
| Linux | L3 only | syscall check only |
| Capsicum | L3 + 部分 L2 | capability mode flag |
| seL4 | L3 + formal proof | formal verified |
| jhyy_OS | L1 + L2 + L3 | 编译期主 + 运行期兜 |
