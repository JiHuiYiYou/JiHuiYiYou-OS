## § 1 地址空间

- 64-bit paging(amd64 4-level paging)
- per-process 隔离
- 内核地址空间高位共享(具体布局待 v0.0.2)
- 内核物理地址布局:待 v0.0.2,本节占位

### 1.1 虚拟地址布局(草案)

```
高位: 内核共享(待 v0.0.2 细化)
  - 内核代码段
  - 内核数据段
  - 内核堆
  - 内核栈(per-thread)

中位: per-process 地址空间
  - 用户代码段
  - 用户数据段
  - 用户栈(per-thread)
  - mmap 区域

低位: 保留 / 平台用
  - 0x0 - 0x10000: null page + bootloader 残留
```

## § 2 线程

- 进程 = 1 个或多个线程
- 线程 = 调度单位
- 共享进程地址空间, 不共享寄存器
- M2 cooperative + 单核起步, M9 加 SMP

### 2.1 线程控制块(TCB,草案)

```jhyy
type TCB = struct {
    tid: ThreadId,             // 线程 ID(进程内唯一)
    pid: ProcessId,            // 所属进程
    stack_ptr: *u8,            // 当前栈指针
    stack_base: *u8,           // 栈基址
    stack_size: usize,         // 栈大小
    saved_regs: SavedRegs,     // 寄存器现场
    state: ThreadState,        // Ready / Running / Blocked / Dead
    caps: [*CapHolder],        // 线程级 cap refs
}
```

## § 3 Namespace

- **per-process capability namespace**
- 进程持有的 `Cap<T>` 是它自己的,跨进程需 grant
- 文件系统 namespace: 待定(全局 vs per-process mount)— **倾向 per-process mount**(跟 cap namespace 一致)

### 3.1 cap namespace

```jhyy
type CapTable = struct {
    entries: [CapEntry; 256],   // 进程持有的 caps
    waiver_cap: bool,           // WaiverCap privilege bit
}

type CapEntry = struct {
    cap: Cap<T>,                 // phantom type 隐藏
    valid: bool,                 // 是否有效
    provenance: ProvenanceInfo,  // debug 用
}
```

### 3.2 FS namespace(草案)

- per-process mount table
- mount cap = `Cap<Mount>`
- 进程持有 mount cap = 该 mount 可访问
- 不持有 = 看不见

## § 4 COW fork

- `fork()` = 创建子进程,父子共享地址空间(只读)
- 写时复制(COW)= 任一方写时,内核分配新页
- 节省内存,加速 fork

### 4.1 cap 继承语义

- fork 时子进程继承父进程的 cap table 副本(不是引用)
- 这是 v0.0.1 简化(后续可改为 selective inheritance)
- grant 链不传播(子进程拿到的 cap 跟父进程的 cap 不同 ID)

## § 5 cap closure MVP(2026-08-04 锁)

**问题**: capability 生命周期由谁管理?谁负责 grant?谁负责 revoke?出错时怎么办?

**决策**: 编译器辅助的 explicit closure pattern(无 RAII,jhyy 没 destructor)。

### 5.1 cap 生命周期模板

```jhyy
// 标准 cap 使用 4 阶段(2026-08-05 D17:`IoResult<()>` 单态化为 `IoResultUnit`)
fn use_cap_responsibly(c: Cap<File>) -> IoResultUnit {
    // 阶段 1: 进入 — cap 已经在手上(参数传入)
    if !c.is_valid() {
        return IoResultUnit::Err(SysError::ErrInvArg);
    }

    // 阶段 2: 使用 — 用 cap 做 syscall
    let result = sys_read(c, buf, len);
    match result {
        IoResultUsize::Ok(n) => { /* ... */ }
        IoResultUsize::Err(e) => {
            // 阶段 3a: 出错 — 必须显式处理 cap
            // 选项 A: revoke(c) — 放弃所有权,销毁底层
            // 选项 B: 继续持有 — 让调用方决定
            return IoResultUnit::Err(e);
        }
    }

    // 阶段 3b: 成功 — 决定 cap 命运
    // 选项 A: revoke(c) — 显式放弃
    // 选项 B: grant(c, ...) — 转给别人
    // 选项 C: 隐式 drop — 退出函数,cap 跟着释放(revoke 通知 kernel)
    IoResultUnit::Ok(())
}

// 阶段 3c: 函数返回 — c 自动 drop,触发 implicit revoke 通知 kernel
```

### 5.2 编译器辅助(未来)

- linter 检查:每个 `Cap<T>` 函数出口是否显式处理(显式 grant/revoke 或隐式 drop)
- provenance 跟踪:每个 cap 在哪构造 / 在哪 drop,debug build 可查
- 不强制编译错误(只是 linter warning)— 因为 cap 跨函数移动时静态分析复杂

### 5.3 MVP 简化(M1-M4)

- 暂时不实现 linter
- **编译器在 cap 离开 scope 时(显式 Drop / 函数返回)emit `cap_destroy` syscall**,内核响应,标 cnode slot invalid
- 这条让"kernel 绝不解决语言问题"原则(#5)自洽 —— 生命周期由编译器跟踪,kernel 只响应显式 syscall
- 编程约定:函数出口要么 grant、要么显式 revoke(cap_destroy)、要么让 cap 自然 drop(编译器自动 emit)

## § 6 Hybrid 内存模型(2026-08-04 锁,跟 capability 一致)

| 对象类别 | 内存机制 | 备注 |
|---------|---------|------|
| **Cap** | linear types(单 owner,move/revoke)| 见 [v0.0.1-capability.md § 5](v0.0.1-capability.md) |
| **用户数据** | region types(primary)| jhyy 编译器自身用 arena.jhyy |
| **kernel 临时** | region types | 短生命周期 |
| **硬件 MMIO** | raw pointer + volatile | bypass 类型系统 |
| **跨进程共享** | `unsafe_share` privilege | 单 bit 运行期门控 |
