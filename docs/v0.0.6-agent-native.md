## § 1 核心主张:不是"支持得更好",而是换一种实现手段

### 1.1 computer-use 是能力,截屏只是手段

**computer-use 是"使用计算机"这项能力本身。** 2026 年的实现链条是:agent 截图 → 视觉模型推理 → 输出点击坐标 → 合成输入事件 → 再截图,闭环。

**截屏是这项能力今天唯一能用的实现手段,而且是劣质的那一个。** 它的三个天花板与模型能力无关:

| 天花板 | 数学/工程性质 |
|---|---|
| 概率衰减 | 单步 95% → 20 步整体 `0.95²⁰ ≈ 36%`;50 步仅 7.7% |
| 错误恢复缺失 | agent 点错后世界状态与内部模型脱节,会基于错误认知继续推进,卡进死循环 |
| 安全半径 = 人能做的任何事 | 不是 API 调用,是交出鼠标键盘;不可逆操作风险不可控 |

关键区分:**能力与手段不是一回事。** 业界共识是:一旦目标应用暴露语义(API / DOM / accessibility tree),立刻改用结构化接口 —— 因为那才是这项能力的高质量实现。截屏不是 computer-use,截屏只是 computer-use 的一个差实现。

### 1.2 jhyy_OS 提供第二种实现手段

jhyy_OS = 全栈单一语言(jhyy)+ Type-driven IPC + capability 语言级。这意味着:

> **每个服务天生就是类型化 API。agent 不需要靠像素看。**

别人在给截屏这条路径装更好的眼睛(分辨率适配、grounding 模型、像素增强);jhyy_OS 提供的是**另一条路径** —— 让 agent 拿到 `Cap<T>` 直接调,而不是看图猜。

**注意本 spec 不否认 computer-use**:agent 照样"使用计算机",只是手段从截屏换成类型化契约。差异化的含金量高于 highlights 里列的任何单条 —— 因为它是**换实现手段**,不是**指标提升**。

### 1.3 因此本 spec 的第一条硬约束

🔒 **不为 agent 引入任何"屏幕截图 / 像素流 / 屏幕抓取"通道。**

这条约束的根据不是"computer-use 是错的",而是**"截屏是劣质实现"**:一旦开了截图通道,它的全部脆弱性(分辨率、DPI 缩放、深色模式、弹窗遮挡、瞬时元素)立即回归,且 Type-driven IPC 的存在意义被架空。这条在 § 6.5 对 M8d 复述为更具体的形式。

## § 2 Goals + 5 原则 compliance

### 2.1 设计目标

1. agent 作为 OS 一等消费者时,**权限由类型系统保证**,不靠沙箱约定
2. agent 的错误**可定位到根因**(复用 provenance / ErrChain)
3. agent 的动作**可撤销性由 OS 定义**(模型永远猜不出来)
4. 为"模型作为系统资源"**锁住架构位**,但不现在实现

### 2.2 5 原则 compliance(per `v0.0.0-design.md § 2`)

| 原则 | 本 spec 怎么满足 |
|---|---|
| **可行且简单** | 零新增子系统:`CapBundle` 复用现有 `derive()`;Reversibility 复用 DebugEvent 现有 reserved 位(56B 不变);模型资源层只锁语义不实现 |
| **双线作战** | agent 需求反向推动 jhyy 加 typed handler / `Cap<ModelWeights>`,符合"OS 需求驱动语言扩展" |
| **寄生 Windows** | 全部开发/验证在 Windows + MSYS2 + QEMU/OVMF;无需 NPU 硬件即可完成本 spec 全部内容 |
| **Debug 在语言里** | agent session 的完整可观测性走 DebugEvent + provenance,不靠外部日志重建 |
| **Kernel 不解决语言问题** | spec 是语言层 + cap 层;kernel 只执行 cnode 检查与 budget 记账,**不理解"agent"这个概念** |

## § 3 Agent Session 模型:`CapBundle`

### 3.1 现状缺口

现有 cap 模型是 **per-process** 的(`v0.0.1-process-model.md § 3.1` `CapTable`)。给 agent 授权时需要一个**"本次会话的受限 cap 包 + 过期 + 预算"** 模式。

`WaiverCap` 那个 single bit(`v0.0.1-capability.md § 4.2`)已经很接近,差一步形式化。

### 3.2 设计(复用 `derive()`,不新造机制)

```jhyy
type CapBundle = struct {
    caps: [*]CapEntry,      // 从父进程 cap table derive() 出的受限子集
    expiry_ns: u64,         // 相对时间(同 IPC timeout 语义);0 = 进程级
    budget: AgentBudget,    // 预算(见 § 3.3)
    waived: bool,           // 复用 WaiverCap single bit
}

type AgentBudget = struct {
    max_steps: u32,         // 动作步数上限
    max_syscalls: u32,      // syscall 次数上限
    max_infer_tokens: u64,  // 推理 token 上限(预留,post-M11 生效)
    deadline_ns: u64,       // 绝对 deadline
}
```

**生命周期**:`derive_bundle(parent_caps, restrictions, expiry, budget) -> CapBundle`,走现有 `derive()` syscall 路径;过期 = **lazy invalidation**(per Q-OS-008 已闭环,编译器只 emit `is_valid()`,不自动 retry/poll)。

### 3.3 为什么预算是编译期可见的

`max_steps` / `max_syscalls` 在 `CapBundle` 字面量里是 jhyy 常量 → sema 可见 → **超过预算的动作在编译期就能被拒**,不是运行期才 abort。这跟"99% 编译期 + 1% 运行期 waiver"的 Layered TCB(`v0.0.1-capability.md § 6`)完全一致。

| 层 | 检查 | 失败模式 |
|---|---|---|
| L1 编译器 | cap 子集合法性 / 类型匹配 / 常量预算越界 | 编译错误(fail-loud) |
| L2 Runtime | `expiry_ns` / `budget` 动态计数 / WaiverCap bit | 运行期 abort(fail-fast) |
| L3 Kernel | cnode 实际检查 | syscall 错误(fail-safe) |

### 3.4 明确不做

- ❌ 不为 agent 单独立 process(复用现有 process + CapBundle 子集即可)
- ❌ 不做 cap 引用计数(per `v0.0.3-explorations.md § 4.4` 已淘汰)
- ❌ 不做 agent 专用调度 class(见 § 5 DROP)

## § 4 Debug ABI 增补:Reversibility(零字节成本)

### 4.1 问题

computer-use 最怕的是**不可逆操作**(提交、删除、支付)。业界方案是在 prompt 里写"危险操作要确认" —— 但**模型永远猜不出某个动作是否可逆,这件事只有 OS 能定义**。

### 4.2 落位:`v0.0.4-debug-abi.md § 2.2` 现有 `flags` 字段

DebugEvent header 56B 布局中原有一个 `flags: u8, reserved (must be 0)`。用它:

```c
// DebugEvent.flags (u8 @53) 低 2 位复用
//   bit0-1 = Reversibility,bit2-7 保留 (must be 0)
#define DEBUGEVENT_FLAGS_REVERSIBILITY_MASK  0x03

enum Reversibility : u8 {
    Reversibility_Unknown       = 0,  // 未标注 → 保守门控(默认,见 § 4.3)
    Reversibility_Reversible    = 1,  // 可完全撤销
    Reversibility_Compensatable = 2,  // 不可逆但有已登记补偿动作
    Reversibility_Irreversible  = 3,  // 不可逆
};
```

### 4.3 默认值必须是 fail-safe

**关键决策**:`0b00 = Unknown`,**不是** `Reversible`。

理由:未标注的事件若默认 Reversible,agent 会放行本应门控的动作 —— 这是**危险的默认值**。改判为 Unknown 后:
- 老事件 `flags = 0` → Unknown → 进入门控(向后兼容且保守)
- 显式标注才享受"免门控"
- 与 pragma "unknown 状态应该 fail-loud 而非 silently pass" 一致

### 4.4 成本

| 项 | 影响 |
|---|---|
| DebugEvent header 尺寸 | **56B 不变** |
| padding / 对齐 | **无变动**(`_pad` @54 仍 2B) |
| 向后兼容 | ✅ 老事件 flags=0 语义合法 |
| 新增字段 | **0** |

### 4.5 门控策略(建议,MVP 不强制)

| Reversibility | agent 自主? |
|---|---|
| Reversible | ✅ 可自主重试 |
| Compensatable | ⚠️ 执行前登记补偿动作,失败自动回滚 |
| Irreversible | ❌ 必须人工确认门控 |
| Unknown | ❌ 按 Irreversible 处理(保守) |

## § 5 模型/推理资源层:只锁语义位,不实现

### 5.1 业界命题(须回应,但不实现)

当 OS 的一等消费者是 agent 时,业界正在争论:**模型是否应成为与进程、文件、网络并列的第四类系统资源?** 具体落点是 NPU 调度、KV cache 跨进程共享、模型权重的存储抽象。

本 spec 的立场:**锁住语义位,实现推 post-M11。**

### 5.2 锁定的语义位(用现成 phantom type 表达,零新机制)

```jhyy
type Cap<ModelWeights> = ...  // 只读权重 region;跨进程共享安全(不可变)
type Cap<InferCtx>     = ...  // 推理上下文,含 KV cache region(per-session)
```

内存归属直接落现有 hybrid 模型(`v0.0.2-foundation-revision.md § 3.2`):

| 对象 | 归属类别 | 说明 |
|---|---|---|
| 模型权重 | region types(只读 mmap 共享) | 不可变 → 跨进程共享安全,无需 `unsafe_share` |
| KV cache | region types(per-session) | 跟 `CapBundle.expiry_ns` 同生命周期 |
| NPU 寄存器 / MMIO | raw pointer + volatile | 复用现有 MMIO 分类 |

### 5.3 明确 DROP(及理由)

| DROP 项 | 理由 |
|---|---|
| NPU 调度器(sched class) | 违反原则一「可行且简单」;需新子系统,两人量级不可控 |
| KV cache 跨进程共享 | 需 refcount / 失效协议,复杂度高且 MVP 无需求 |
| 模型权重存储抽象(第四类资源) | 是**命题**不是需求;post-M11 再评估 |
| 推理 QoS / 优先级 | 依赖 NPU 调度器,一并推后 |

**结论**:本 spec 承认"模型作为一等资源"是真实命题,但按 § 5.2 只锁语义与 cap 表达。这样即使 post-M11 真做,**不需要回头改 v0.0.1 三章或本 spec 已锁内容**。

## § 6 Milestone 落位:横切属性

### 6.1 决策

**不设独立 milestone。** agent 支持作为横切属性分散进 M3–M11。理由:
- 符合原则五「kernel 不解决语言问题」—— agent 支持主要是语言层 / cap 层的事
- 不拉长主链,M11 时间线不变
- 避免"agent milestone 永远排不上"的死锁

### 6.2 横切映射表

| M | 现有目标 | agent 相关属性(本 spec 增补) |
|---|---|---|
| **M3** | syscall ABI | Type-driven IPC 天然服务 agent;`#[ipc_handler]` 编译期验签名 = agent 可直接消费的类型化 API。**`CapBundle` 定义落此处** |
| **M4** | capability 落地 | `CapBundle` 实施:`derive()` 受限子集 + `expiry_ns` + `AgentBudget` |
| **M5b** | IPC 实现 | provenance 支持 agent session(grant chain 记录 bundle 派生);**DebugEvent Reversibility 落地** |
| **M8a** | 早期 UI | framebuffer persistent(agent 可观察终端状态,无需截图) |
| **M8d** | compositor | **Wayland-style + `Cap<Surface>`;🔒 禁截图兜底**(见 § 6.5) |
| **M9** | SMP | 无新增(agent 不依赖 SMP) |
| **M11** | 自举 OS 跑 jhyy 编译器 | **收口**:验证 agent 在 jhyy_OS 上原生运行 |

### 6.3 与 v0.0.4-gui-explorations 的关系

`v0.0.4-gui-explorations.md § 2.7` 已选 **M8a 走 F(自研 minimum)、M8d/M12 走 A(Wayland-style)**。本 spec 与该选择**完全一致**,并追加 § 6.5 硬约束。

### 6.4 双向关系(复用现有洞察)

`v0.0.4-gui-explorations.md § 1.3` 已识别 GUI ↔ compiler 双向循环。本 spec 扩展为 **agent ↔ compiler**:

- **正向**:agent runtime 需要 typed handler → 强化 sprint 3g(`&mut` + lifetime);需要 provenance → 强化 M5b
- **反向**:`Cap::provenance()` / ErrChain / KernelState → agent 直接可消费,**不需要截图、不需要日志重建**

### 6.5 🔒 M8d 硬约束(防稀释)

> **M8d compositor 必须走 typed IPC**(`Cap<Surface>` + 协议消息类型),**禁止**引入任何"为 agent 提供屏幕截图 / 像素流 / 屏幕抓取"的 fallback 通道。

理由:这条是本 spec § 1.3 论点最容易被后续 sprint 稀释的地方 —— 一旦某个 sprint 说"先截图顶一下",computer-use 的全部脆弱性立即回归,且 Type-driven IPC 的存在意义被架空。**提前锁死。**

## § 9 开放问题

### 🟡 Q-AGENT-001:「跑 Claude Code」与「纯 jhyy from day 1」的张力

`v0.0.3-explorations.md § 6.3` 把"在 jhyy_OS 上跑 Claude Code"列为 stretch goal。2026 年这句话已不是玩笑 —— 它是**有商业与学术含义的目标**。

但它意味着:**必须接受外部 agent(非 jhyy 编写)成为内核的一等消费者**,这与「纯 jhyy from day 1」(`design-log.md § 2`)存在张力。

- 张力点 1:外部 agent 的二进制格式 —— `.jhyynb` 还是别的?
- 张力点 2:外部 agent 如何获得首个 `CapBundle`?(init 进程 grant 链的起点)
- 张力点 3:是否违背"kernel + driver + shell + app + build tool 全 jhyy"?

**建议**:在 `coordination.md § 2` 单独开 Q,不在本 spec 内闭环。

### 🟡 Q-AGENT-002:budget 耗尽由谁 abort?

`AgentBudget` 有 `max_steps` / `max_syscalls` / `deadline_ns` 三项。L1 只能拒**常量可见**的越界;动态计数越界由谁执行?

- 选项 A: kernel 在 cnode 检查时顺带记账(L3)
- 选项 B: 用户态 session manager(L2)

倾向 A(更靠近 ground truth),但会增加 syscall handler 复杂度。**待 M4 实施时决定。**
