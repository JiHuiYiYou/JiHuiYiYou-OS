# M8d / M12 排期修订建议（基于 GUI 子系统研究报告）

> 来源：`jhyy_gui_subsystem.md` §9、§12。本文只提取"前置依赖 + 排期调整"，供作者确认后并入 `docs/plans/roadmap/`。

## 一、核心结论

**M8d 不能直接进入协议功能扩张，必须在 sprint 3g / 3i / 3j 之后实施。**
M12 应从"工具包功能集"重定义为"策略合规后的安全 API 稳定集"。

理由：GUI 的 4 个真正阻塞项全部落在语言与内核层，compositor 协议层无法独立闭合：

| 阻塞项 | 归属 sprint | M8d 是否可绕过 |
|---|---|---|
| `Cap<Shm>` 与共享映射语义 | 3i | 否 |
| 异步 revoke 的 epoch / ack 模型 | 3j | 否 |
| D16 IDL 确定性 | 3g | 否 |
| framebuffer 与 VSync 驱动接口 | 3j | 否（可先做软件合成兜底） |

## 二、修订后的依赖链

```
3g (Cap / ID ledger / D16)
   └─ 3i (Shm 内核对象、sys_map_shm、mapping ledger)
         └─ 3j (revoke epoch/ack、framebuffer、VSync)
               └─ M8d (compositor 协议层 + 最小闭环原型)
                     └─ M12 (toolkit 安全 API 稳定集)
```

## 三、M8d 最小闭环（不冻结协议）

在 3g–3j 形成"**类型检查 + mapping ledger + epoch revoke**"最小闭环前，M8d 只做：

1. compositor 独立 capability 域的最小骨架（不含完整 Wayland 功能集）
2. `Cap<Surface>` move / `Cap<Buffer>` attach-commit-release 状态机原型
3. client 端双缓冲 + commit 移交可见性的属性测试
4. 幽灵 surface 反例测试（inflight commit 与 client 死亡竞争）

**此时协议版本保持 `GUI_PROTOCOL_VERSION = 0`，明确标注"草案，可破坏变更"。**

## 四、M12 重新定义

- **旧定义**：GUI 工具包（功能集）
- **新定义**：在 M8d 最小闭环经原型验证、revoke/TOCTOU/确定性全部通过验收矩阵后，
  冻结的**安全 API 稳定集**

即：M12 的交付物不是"功能多"，而是"**权限、生命周期、确定性三条不变式可机器检查**"。
