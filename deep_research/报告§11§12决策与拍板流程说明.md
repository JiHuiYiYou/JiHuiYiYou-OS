## 0. Preamble

### 0.1 Scope

This document specifies the **user-space protocol between a client/toolkit domain and the compositor service**. It does **not** specify:

- the kernel ABI (syscall numbers, page-table operations, `sys_map_shm`);
- the GPU command stream or display driver internals;
- compositor-internal scene-graph algorithms (focus policy, layout).

Those are referenced only at **interface boundaries** (§5, §8), so that this protocol can be implemented against a stable capability contract without depending on kernel internals.

### 0.2 Decision labels

Per **principle 5** (language/kernel boundary), every normative statement below carries one of:

| Label | Meaning |
|---|---|
| `🔒 LOCKED` | Architecture decision already ratified. This doc only records and refines it. |
| `🤝 PROPOSED` | Not yet ratified. Implementable as a design candidate. |
| `🔧 IMPLEMENTATION-DEFINED` | A detail whose exact value (opcode number, queue depth, timeout) does not affect the protocol contract; the implementation may choose, but MUST publish. |

> `🤝` items advance to `🔒` after the corresponding decision is ratified and confirmed in source files (`coordination.md` / `v3.x spec` / etc.). Code generation against `🤝` items is exploratory.

## 1. Protocol foundations

### 1.1 Topology

(`🔒 LOCKED`, D-GUI-3)

```
┌─────────────────────────────────────────────────────────┐
│  client / toolkit domain                                 │
│    holds: Cap<Compositor>, Cap<Surface>, Cap<Buffer>      │
│    owns:  Cap<Shm, RW> (pixel region)                    │
└──────────────────────┬──────────────────────────────────┘
                       │ typed IPC, D16 cap-offsets
                       ▼
┌─────────────────────────────────────────────────────────┐
│  compositor service  (independent user-space domain)     │
│    holds: Cap<Seat>, Cap<Framebuffer>, Cap<Gpu>          │
│    policy: scene graph, focus, scanout, input routing    │
└──────┬───────────────────────────────────────┬──────────┘
       │ sys_map_shm RO/RW, revoke channel     │ seat authority
       ▼                                       ▼
┌──────────────┐                    ┌──────────────┐
│  kernel       │                    │ input driver │
│  Cap ledger,  │                    │ domain       │
│  AS maps,     │                    │ (raw events) │
│  Shm regions, │                    └──────────────┘
│  revoke epoch │
└──────────────┘
```

Three boundaries, each with a single responsibility (study §2):

- **credentials** flow in user space (capabilities, move/borrow rules);
- **policy** executes in the compositor (who may see what, focus, scanout);
- **mappings** are audited by the kernel (page tables, revoke, epoch).

### 1.2 Versioning (`🔒 LOCKED`)

```
GUI_PROTOCOL_VERSION = 0
```

- The protocol is **append-only**: new interfaces, requests, events, and capability parameters may be added **only at the end** of existing lists.
- A **breaking change** (removing a request, changing a capability's move semantics, reordering cap-offset fields) requires `GUI_PROTOCOL_VERSION := 1`, negotiated at connection setup.
- **Open**: the exact negotiation handshake (how a client discovers the server's supported version) is **not** specified here; it belongs to the connection/bootstrap interface and is `🔧 IMPLEMENTATION-DEFINED`.

### 1.3 Capability boundary axiom (`🔒 LOCKED`, D-GUI-5)

> **Axiom C1.** No message field, anywhere in this protocol, may contain:
> - a physical or virtual address;
> - a file descriptor, UNIX socket, or any OS-specific handle;
> - a CSpace-internal index or CNode slot number;
> - a GPU resource id, virtqueue index, or driver-internal token.
>
> Every cross-domain object is referenced exclusively by a `Cap<T>` value carried in the **cap table** (§3), addressed by a D16 offset.

This axiom is what allows the same protocol to run over the existing jhyy IPC transport **and** over a future in-kernel bypass path without changing message semantics.

## 2. Capability contracts (`🔒 LOCKED`, D-GUI-1/2)

This section is the **canonical encoding** of the two ratified decisions on shared memory and audited sharing. It overrides any contradictory suggestion in the architecture study.

### 2.1 The five capability types

| Type | Initial holder | Rights bits | May move? | May clone? | May derive? | Revoke semantics |
|---|---|---|---|---|---|---|
| `Cap<Compositor>` | init → client | `CreateSurface`, `BindSeat(query)` | yes (move-only) | no | no | revoke ⇒ no further creation |
| `Cap<Surface>` | compositor → client | `Attach`, `Commit`, `SetInputRegion`, `Destroy` | yes (move-only) | no | no | client death ⇒ cascade revoke |
| `Cap<Buffer>` | shm owner → toolkit | `Write` (owner only) | logically borrowed in `AttachBuffer`, never transferred | no | no | released via `BufferReleased` event |
| `Cap<Shm>` | shm service → creator | `RW` or `RO`; `Map`, `Derive`, `Destroy` | yes (move-only) | **no** (D-GUI-1) | **only收缩**, via `unsafe_share` (D-GUI-2) | region revoke ⇒ all mappings invalidated |
| `Cap<Seat>` | input service → compositor | `Focus`, `Listen`, `SetCursor` | **single owner** (compositor only) | no | listen-only child caps, never to clients | policy service may revoke |

### 2.2 Ownership model: handle-linear, mapping-shared (`🔒 LOCKED`, D-GUI-1)

```
Cap<Shm> instance  ──move-only, 8-byte cnode reference──►  kernel Region object
                                                              │
                       ┌──────────────────────────────────────┘
                       │  Mapping ledger (kernel-side, not a GC)
                       ▼
        ┌──────────────────────┬──────────────────────┐
        client AS: RW mapping  │  compositor AS: RO    │  (optional) GPU AS: W,
        (creator, sole writer)│  mapping (default)    │  only via unsafe_share
        └──────────────────────┴──────────────────────┘
```

- **`Cap<Shm>` is linear** (same rule as every other `Cap<T>`): exactly one owning slot, move-only, no `Copy`. **This is non-negotiable**—it preserves `is_valid()`, use-count tracking, and byte-equal validation.
- **What is shared is the Region's page set**, recorded in a kernel **mapping ledger** as `(Region, AddressSpace, range, rights, epoch)` tuples. This is **object-relationship metadata**, not garbage-collection: no refcount, no finalizer, no runtime scan. It exists solely so revoke can find every mapping and invalidate it.
- Therefore the project's **"no GC" principle remains intact**: there is no runtime object-graph traversal, no weak/strong distinction, and no cycle detection.

### 2.3 Permissions:收缩-only derivation (`🔒 LOCKED`)

```
derive(parent: Cap<Shm, rights>, requested: Rights) -> Result<Cap<Shm, requested>, EPERM_RIGHTS>
    where requested ⊆ parent.rights
```

- Derivation **can only narrow** the permission set (e.g. `RW → RO`). It can never grant a bit absent from the parent.
- The returned child is itself a **linear `Cap<Shm>`**—same 8-byte layout, same move rules. It is **not** a `SharedCap<T>`. (This is the formal statement of "不引入通用 `SharedCap`".)

### 2.4 `unsafe_share`: the audited exception (`🔒 LOCKED`, D-GUI-2)

> **Rule U1.** A `RW → W` or `RW → RW` derivation across domain boundaries is permitted **only** through `unsafe_share`, and only when all of the following hold:
>
> 1. The call site is explicitly annotated (`unsafe_cap` / `unsafe_share`);
> 2. A compile-time audit records `(region_id, source_domain, target_domain, granted_rights, epoch)`;
> 3. The封送 (marshalling) payload carries `region_id`, `rights`, and `epoch` together—**never** an address;
> 4. The target domain's use of the resulting mapping is bounded by an explicit fence/ack lifecycle.

- **Default path is `RW → RO` via ordinary `derive`** (no `unsafe_share` needed). This is the case for every normal client→compositor pixel buffer.
- `unsafe_share` exists for a **small, auditable set** of cases: compositor granting a GPU domain write access to a scanout buffer; a trusted scanout controller. It must **not** become the everyday shared-memory mechanism—that would defeat D-GUI-1.
- **Open**: the concrete audit-log format and whether the compiler emits warnings on unannotated cross-domain `derive` are `🔧 IMPLEMENTATION-DEFINED` (language v3.x territory, sprint 3g).

### 2.5 What this protocol does **not** assume

To prevent the protocol from leaking kernel assumptions:

- It does **not** assume a Linux-style `mmap`/`munmap` API;
- It does **not** assume file descriptors or UNIX sockets;
- It does **not** assume a specific page size (the compositor sees a `Rect` in pixels plus a byte stride; layout validation is the writer's responsibility);
- It does **not** assume GPU implicit fencing—every GPU access must go through the same explicit release state machine (§4.3).

## 3. Wire format

### 3.1 Layered layout

Every message is a contiguous byte sequence:

```
┌────────────────────────────────────────────────────┐
│  header  (16 bytes, fixed)                          │
├────────────────────────────────────────────────────┤
│  body    (fixed-length IDL fields, no pointers)     │
├────────────────────────────────────────────────────┤
│  cap_table (cap_count × D16 offset, sorted)         │
├────────────────────────────────────────────────────┤
│  payload  (optional structured bytes, length in     │
│            body by canonical field)                  │
└────────────────────────────────────────────────────┘
```

### 3.2 Header (`🔒 LOCKED`, D16)

```
struct MessageHeader {
    msg_tag:    u16,   // message type + version + parameter schema
    flags:      u16,   // reserved for future; MUST be 0 in v0
    body_len:   u32,   // length of body, in bytes
    cap_count:  u16,   // number of D16 offsets in cap_table
    reserved:   u48,   // MUST be 0; reserved for future capability flags
}
// Total: 16 bytes. All fields little-endian. No padding.
```

Rationale for the 6-byte `reserved`: it future-proofs the header for capability-flag extensions without changing its size or breaking byte-equal validation.

### 3.3 Cap-offset table (D16)

- Offsets are **D16 (16-bit, big-endian at wire level, decoded to native by the receiver)** and numbered **from 0 in declaration order** of the cap-bearing fields in the IDL.
- The `cap_table` is sorted by offset; duplicate offsets refer to the **same** `CapId` (canonical, no repetition in storage).
- **On receive**, the kernel/Cap layer:
  1. resolves each offset to a `CapId` against the sender's CSpace;
  2. validates **type and rights** (rejecting the whole message on mismatch—**fail-closed**);
  3. rewrites offsets into the receiver's CSpace;
  4. only then invokes the IDL decoder, which statically knows which fields are cap positions (no integer misread as a cap).

### 3.4 Byte-equal axiom (`🔒 LOCKED`, D16 + self-build)

> **Axiom B1.** Given identical protocol source, IDL options, and input, two independent serializations MUST produce **identical bytes**.

Enforced by (study §1, §11.2):

1. canonical field ordering (the order written in the IDL is the order on the wire—**no hash-map iteration**);
2. fixed-width enums (no compiler-default sizes);
3. length-prefixed variable data;
4. **no pointer values** in payload (C1 forbids them);
5. **no dependence on hash order** anywhere in the code generator;
6. auxiliary containers use sorted iteration or a fixed seed.

> **Note**: this is a stronger requirement than ordinary wire compatibility—it is necessary for jhyy's self-build byte-equal closure and replay tests. It is a **property of the protocol compiler**, which therefore enters the trusted base (study §1).

### 3.5 Primitive types (`🔧 IMPLEMENTATION-DEFINED`)

```
struct PixelFormat { fourcc: u32, bits: u8, flags: u16 }
struct Rect        { x: i32, y: i32, w: u32, h: u32 }
struct Region      { rects: Array<Rect, MAX_RECTS> }   // damage / input region
struct EventBody   { kind: u16, payload: Bytes<64> }

struct SurfaceConfig {
    width:  u32,
    height: u32,
    format: PixelFormat,
    role:   SurfaceRole,   // e.g. `Normal`, `Cursor`, `Scanout` (v0: only `Normal`)
}

enum SurfaceRole : u8 { Normal = 0, Cursor = 1, Scanout = 2 }
// `Cursor`/`Scanout` are reserved for future use; v0 servers MAY reject them.
```

**Open**: `MAX_RECTS`, the exact `Bytes<N>` representation, and the fourcc registry are `🔧 IMPLEMENTATION-DEFINED` and MUST be published by the implementation.

## 4. Core interfaces (IDL)

> Syntax below is **specification IDL**, not a commitment to jhyy surface syntax. An IDL compiler generates (a) capability-aware bindings and (b) the cap-offset/msg_tag tables. The generated code is what client/toolkit and compositor actually link against.

### 4.1 Interfaces

```idl
interface Compositor {
    CreateSurface(parent?: Cap<Surface>, cfg: SurfaceConfig) -> (s: Cap<Surface>);
    CreateBuffer (region: Cap<Shm>, fmt: PixelFormat, stride: u32, rect: Rect) -> (b: Cap<Buffer>);
    GetSeat      (kind: SeatKind) -> (seat: Cap<Seat>);
}

interface Surface {
    AttachBuffer(b: Cap<Buffer>, x: i32, y: i32, commit_seq: u64);
    Commit       (damage: Region, commit_seq: u64) -> (cb: FrameCallback);
    SetInputRegion(region: Region);
    Destroy      () -> ();
}

interface Buffer {
    Release();   // client regains write authority only after BufferReleased event
}

// One-shot callback objects (capability-bearing events)
interface FrameCallback {
    Done(presented_at: u64, commit_seq: u64);
}
```

### 4.2 Lifecycle invariants (`🔒 LOCKED`, D-GUI-9)

> **Invariant L1 — monotonic commit.**
> `commit_seq` MUST strictly increase on a given `Cap<Surface>`. A duplicate or out-of-order value is an error (`ESEQ_COMMIT`). **Wrap-around is forbidden**; if the 64-bit space is exhausted, the surface MUST be destroyed and recreated.

> **Invariant L2 — exclusive write window.** Between `AttachBuffer` and the corresponding `BufferReleased`, the **client MUST NOT** write to the buffer's pixels; the compositor (or scanout hardware) is the sole reader. Toolkit type-state enforces this locally; the compositor enforces it per-buffer; the kernel provides the final防线 via mapping rights.

> **Invariant L3 — release before reuse.** A client may resume writing a buffer **only after** receiving `BufferReleased` for it.

> **Invariant L4 — destroy cascades.** `Surface.Destroy` (or the client's `Cap<Surface>` being revoked) moves the surface to `Dying`; all un-acknowledged buffers enter revoke (§6).

These four invariants jointly prevent the classic Wayland failure mode: a client writing into a buffer while the compositor (or GPU scanout) is still reading it (study §4, [3]).

### 4.3 GPU and cross-device note

Even when a buffer is subsequently used as a GPU scanout target, **L2 still applies**: the GPU domain receives its access through `unsafe_share` (§2.4) and must respect an explicit fence/ack. The protocol does **not** define implicit synchronization. (This keeps the capability layer's revoke guarantee honest—if the GPU could silently retain access, "revoke complete" would be a lie.)

## 5. Kernel/protocol boundary (contract, not implementation)

This section is the **only** place kernel details appear, and only as **interface contracts** the protocol relies on. Implementation lives in sprints 3i/3j.

### 5.1 Required kernel primitives (`🔒 LOCKED` in spirit, **signature TBD**)

| Primitive | Semantic contract | Protocol use |
|---|---|---|
| `shm_create(region, perms)` | create a Region and return its `Cap<Shm>` root | before `CreateBuffer` |
| `shm_derive(src, rights)` | derive a收缩权限 child (§2.3) | `unsafe_share` path |
| `shm_map(cap, as, flags)` | install a mapping in an address space | client writes; compositor reads RO |
| `unmap(range, epoch)` | remove a mapping, gated by epoch | revoke (§6) |
| `cap_revoke_async(id, mode)` | begin logical invalidation | client death, surface destroy |
| `cap_ack_revoke(id, epoch)` | confirm user-space cleanup done | bounded async revoke |
| `display_alloc_surface` / `map_framebuffer` | allocate scanout + bind compositor's `Cap<Framebuffer>` | single-output software compositor (M8d v0) |
| VSync notification | per-output timeline tick | `FrameCallback.Done` |

### 5.2 Shm region ↔ mapping split (`🔒 LOCKED`, D-GUI-6)

- A `Cap<Shm>` **identifies a Region**; it is **not** the mapped memory itself.
- Multiple read-only mappings may exist (client AS + compositor AS), each an independent ledger entry.
- **Wire representation of `Cap<Shm>`** (the 8-byte layout, rights encoding, epoch presence) is `🔧 IMPLEMENTATION-DEFINED` and **must not** be assumed by protocol code. This is intentional: it lets 3i finalize the wire format without churning this document.

### 5.3 What the protocol guarantees vs. what the kernel guarantees

| Concern | Protocol guarantee | Kernel guarantee |
|---|---|---|
| A client cannot forge a cap | type+rights checked at every IPC (§3.3) | Cap ledger integrity |
| A revoked buffer is not accessed | `RevokeBegin` event + L2/L4 | page-table invalidation + epoch |
| Byte-equal wire | Axiom B1 | deterministic ID ledger (CapId/msg_tag/cap-offset) |
| No pointer leaks | Axiom C1 | marshaller rejects raw-address fields |

## 6. Asynchronous revoke and the "ghost surface" closure (`🔒 LOCKED`, D-GUI-7)

The revoke protocol is the **same** state machine the architecture study defined (study §4); this section makes it machine-checkable at the protocol level.

### 6.1 Events

```idl
event RevokeBegin { object: Cap<Object>, epoch: u64, reason: RevokeReason }
event AckRevoke   { object: Cap<Object>, epoch: u64 }   // client/compositor → kernel
event BufferReleased { buffer: Cap<Buffer>, epoch: u64 }
```

```
                client alive                    client dies / Destroy
              ┌────────────────────┐
              │                     │
              ▼                     ▼
   ClientOwns ──AttachBuffer──► Attached ──Commit──► Committed
                                    │                    │
                                    │ Release/epoch      │ Destroy / revoke
                                    ▼                    ▼
                              Released              Dying ──all mappings acked─► Destroyed
```

### 6.2 Four-phase protocol (`🔒 LOCKED`)

1. **Logical invalidation**: client death or `cap_revoke_async(region_id, mode)` ⇒ kernel increments `epoch` and marks Region `logically dead`. New derivations/attaches are rejected.
2. **Mapping protection**: kernel **immediately** invalidates all page-table entries for the Region (shootdown/IPI if needed). Any in-flight scanout sees a stale mapping only until the next VSync boundary.
3. **Explicit confirmation**: compositor receives `RevokeBegin(region_id, epoch)`, stops taking new references, and sends `AckRevoke(epoch)` within the grace period.
4. **Resource release**: when **all** mappings and in-flight commits are confirmed, kernel frees physical pages.

### 6.3 Bounded async (`🔒 LOCKED`, grace period `🔧 IMPLEMENTATION-DEFINED`)

Each revoke record carries:

- a deadline epoch;
- the expected set of acknowledgers;
- a grace period (default **TBD**; the implementation MUST publish it).

On timeout, the kernel **may** force-reclaim or report a policy violation to the monitor. This prevents a malicious or stuck compositor from holding resources indefinitely, while ordinary errors do not crash the system.

### 6.4 The four ghost-surface paths (study §4, made explicit)

| Path | Cause | Closure mechanism |
|---|---|---|
| A | Client dies before inflight commit arrives | compositor indexes surfaces by `(client_id, surface_id)`; all move to `Dying` on client-cap revoke |
| B | Revoke arrives before compositor processes it | kernel invalidates mappings + increments epoch; user space validates epoch on every message |
| C | Compositor scans pixels while Region is freed | page-table unmap precedes physical free; scan uses epoch-guarded snapshot |
| D | Focus surface replaced/revoked | seat commit carries epoch; event delivery re-validates the full focus chain |

**Implementation note**: C is the expensive case. M8d v0 uses **mapping protection** (unmap first). **Copy-on-revoke** is a later optimization, must be quota-bounded, and must name who bears the copy cost.

## 7. Input: seat policy (`🔒 LOCKED`, D-GUI-3)

### 7.1 Single-owner rule

(`🔒 LOCKED`, D-GUI-3)

- `Cap<Seat>` has **exactly one owner**: the trusted compositor. It is **never** transferred to a client.
- Clients receive only `InputEvent { seat, target: Cap<Surface>, event }`. They **never** see the seat capability.

This is the **necessary and sufficient** condition for defeating keyloggers: there is no capability path by which a client obtains raw input. Filtering key names after the fact cannot help if a client already holds the seat.

### 7.2 Focus-epoch validation (`🔒 LOCKED`, D-GUI-9 family)

```text
Seat {
    root_caps:      Cap<Seat>,
    focus:          SurfaceId,
    focus_epoch:    u64,
    exclusive:      Option<PolicyCap>,   // lock-screen / drag, temporary
    key_states:     Map<Keycode, OwnerSurface>,
}
```

Event delivery:

1. input interrupt → raw event enters trusted seat;
2. compositor snapshots `(focus, focus_epoch)`;
3. event wrapped as `InputEvent`, sent to target;
4. **immediately before delivery**, re-verify `focus == target && epoch still valid`;
5. on completion, return `event_seq`.

Any `focus_epoch` change invalidates all pending events. This is the protocol-level expression of Nitpicker's "deliver input only to the focused client" rule (study §6, [2]).

### 7.3 Capability split (`🔒 LOCKED`)

| Capability | Responsibility |
|---|---|
| `Cap<Framebuffer>` | scanout / display output |
| `Cap<Gpu>` | GPU commands and accelerated resources |
| `Cap<Seat>` | input focus and event routing |
| `Cap<Shm>` | shared-memory region and mappings |

Compositor may aggregate these, but **must** keep audit boundaries: e.g. `Cap<Seat, Focus>` MUST NOT derive into `Cap<Shm, ReadAll>`. Key repeat is centralized in the compositor/seat service (consistent with Wayland 1.24's approach, study §6).

## 8. Error model (`🔒 LOCKED`)

Errors are part of the protocol and MUST be checked by generated bindings.

```idl
enum GuiError {
    EPERM_RIGHTS     = 1,   // permission insufficient
    ESEQ_COMMIT      = 2,   // commit_seq non-monotonic or wrapped
    EEPOCH_REVOKE    = 3,   // mapping or message stale (epoch mismatch)
    EBAD_CAPOFF      = 4,   // D16 offset out of range or type mismatch
    EBUSY_SCANOUT    = 5,   // buffer still being displayed
    ENOMEM_LAYOUT    = 6,   // stride / format / alignment unsupported
    ETIMEOUT_REVOKE  = 7,   // grace period elapsed (§6.3)
}
```

**Conversion rule**: kernel errors are mapped to `GuiError { tag, code, cap_id?, epoch? }`. **Diagnostics MUST NOT** include raw addresses, page-table entries, CSpace layout, or driver internals—error messages themselves are a side channel (study §5).

## 9. Milestone M8d: scope and sequencing (`🔒 LOCKED`, D-GUI-4)

### 9.1 M8d v0 feature set (`🔒 LOCKED`, D-GUI-10)

The minimum correct compositor ships:

- `Compositor`, `Surface`, `Buffer`, `Seat` interfaces;
- **single output**;
- **software compositor** (linear scan + dirty rectangles, ARGB8888 only);
- **pointer input** only (single seat; keyboard repeat and touch deferred);
- `FrameCallback` (driven by VSync).

Explicitly **out of scope** for v0: XDG shell completeness, multi-seat, drag-and-drop, data device, screen capture, HDR, GPU compositing, full tablet support. These are **incremental** additions once the capability core is stable.

### 9.2 Dependency order (non-negotiable)

```
3g  (Cap / ID ledger / D16 deterministic marshalling)
  └─ 3i (Cap<Shm> region, RO/RW derive, dual-AS mapping)
       └─ 3j (revoke epoch/ack, framebuffer mapping, VSync)
            └─ M8d (wire spec + scene graph + single seat + software compositor)
                 └─ M12 (toolkit API stable set: pool, double-buffer,
                          event loop, widgets, fuzz suite)
```

**No protocol freeze before 3j.** If the protocol is finalized earlier, every subsequent Shm/revoke semantic change becomes a **breaking wire change** (study §8/§9). This ordering is the single most important outcome of the architecture study.

### 9.3 M12 redefinition (`🔒 LOCKED`, D-GUI-4)

M12 is **not** "deliver toolkit features." It is: **"deliver a stable API on top of stable capabilities."** A minimum toolkit MUST label every public API with:

- whether it holds a cap;
- whether it moves a cap;
- whether it may revoke;
- whether it may block;
- whether it is thread-safe.

IDL-generated bindings are mandatory; **toolkits MUST NOT cache raw mappings**.

## 10. Acceptance matrix (study §10, protocol-facing subset)

| Dimension | Acceptance point | Pass criterion | Key反例 |
|---|---|---|---|
| Cap linearity | `Cap<Surface>`, `Cap<Shm>` not `Copy` | compile + runtime reject; moved value unusable | cross-thread, exception path, IPC replay |
| Shm shared | client writes, compositor reads RO | pixels match, no page fault | RO端 attempt write; unaligned map |
| Revoke | client crash / region revoke | mappings invalidated immediately; reclaimed after ack | revoke-during-scan, grace timeout |
| Ghost surface | inflight commit vs. death race | no read of freed frame; surface → Destroyed | delayed commit, out-of-order IPC, scanout preemption |
| TOCTOU | attach/commit/release race | commit_seq monotonic; epoch check | old buffer re-attach, dual writer |
| Input isolation | seat focus routing | non-focused client receives zero raw keys | forged seat, focus race, exclusive deadlock |
| Determinism | D16 + ID ledger | byte-equal across build dirs and `-j1/-j4/-j8` | hash randomness, sort variance, pointer混入 |
| Performance | software compositor + VSync | p95 present latency within budget | many surfaces, frequent commit, revoke storm |

**Rule**: testing "a buffer displays" proves **nothing** about security. Every release needs the full matrix, plus property-based fuzz on the wire format (study §10).

## 11. Backward-compatibility and extension notes

- **v0 → v1**: a major version bump is required for any of: removing a request, changing a cap's move semantics, changing the header layout, or reordering cap-offset fields. Adding new interfaces, requests, events, or cap parameters at the **end** of existing lists is v0-compatible.
- **Unknown fields**: a receiver MUST reject a message containing a `msg_tag` or cap type it does not recognize (fail-closed), rather than skipping. This is what makes append-only safe.
- **Quota/DoS** (`🔧 IMPLEMENTATION-DEFINED`): surface count, buffer-pool size, pending-revoke queue depth, and revoke grace periods MUST all be bounded and documented. A malicious client must not be able to pin resources via an in-flight commit indefinitely (§6.3).

## 12. Out-of-scope / future work

Items deliberately **not** specified here (tracked for post-M8d):

- Multi-output and output hotplug;
- GPU acceleration and virtio-gpu backend (depends on `Cap<Gpu>` + explicit release);
- DRM formats, HDR, color management;
- Drag-and-drop, data device, clipboard policies;
- Multi-seat and touch;
- Screen capture / remote desktop (requires a dedicated capability-gated protocol);
- XDG-style window-management policies (built into M8d compositor but separated from the core protocol).

Each will be a **new interface added in append-only fashion** under a future minor version, or a breaking change under a new major version (§11).
